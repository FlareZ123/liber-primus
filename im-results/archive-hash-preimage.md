**Current assessment (2026-11-13 update):** nine independently executed **bounded source-native test groups** report zero matches. A separate 65-case gate of 13 literal strings from the later, unverified 2019 onion/domain/video claim also found zero matches under five 512-bit digest families. ## Why this test exists

The authenticated solved LP2 page 56, AN END, specifies a 128-hex-character digest and refers to an unknown deep-web page. The reference does not identify an onion hostname, digest algorithm, or the canonical byte serialization of the page. Its 64-byte length does not identify a unique hash algorithm.

**2014 archival transcription provenance, with dependency corrected.** The source JPEG of physical LP2 p56 (combined corpus `73.jpg`) visually prints the 128-hex-character target in five lines of respective lengths **26, 25, 25, 27, 25**. Michel Oosterhof's [2014-05-11 Git commit `06f57643821f1cadf597471c2b9c813bd08d2e37`](https://github.com/micheloosterhof/cicada-2014/commit/06f57643821f1cadf597471c2b9c813bd08d2e37), metadata timestamp **21:56:12Z**, message **“page 56”**, adds **both** `stage11/ky2khlqdf7qdznac.onion/56.txt` (exactly those five literal-hex lines) **and** `56.bin` (exactly the 64 bytes `bytes.fromhex(targetHex)`) **in the same commit**. It also adds a README explaining the `xxd -r -p` conversion pattern for another numbered file; the direct relation is manifest in these two identical representations. The preserved `56.txt` is **133 bytes = 128 literal hex characters + five LF line endings**. Concatenate the five line strings *before* `bytes.fromhex` (individual lines 2, 3 and 5 have odd nibble counts); the 64 resulting bytes have SHA-256 `0911bf3c8cc3a73bbb346f82ba65daff3eb81914c4826060ac168bd0f55e267e`, exactly the archived `56.bin` object. This construction was independently executed on the printed line literals; it is not a new preimage. The preceding parent commit `a9201dd469a1a514eb0d8ff8f3449dbe2e7f7462` lacks the binary Git blob. Subsequent commit `1e3e842b460848d8e9342ae47efe453e20443aee` (metadata 2014-05-11 22:09:23Z) relocates this same blob to `stage11/56.bin`. **The binary is best understood as a derivative rendering of the printed hex, not an independent retrieval of the unknown deep-web page, independent corroboration of its digest, or proof of a digest algorithm.** The SHA-1 Git blob object ID `cfd4a08cd8ffa31c8e40c5c7a544d2774ca764a4` and content SHA-256 `0911bf3c8cc3a73bbb346f82ba65daff3eb81914c4826060ac168bd0f55e267e` verify its exact byte representation; compute `b=bytes.fromhex(targetHex)`, `sha1(b'blob 64\0'+b)`, `sha256(b)`. This is historical evidence that a researcher transcribed the page by May 2014, subject to unverified Git metadata; it contributes **no independent input to a target-preimage test**. Full source lineage and cautions are recorded in [the pinned witness metadata](../resources/cicada2014-anend-binary-witness.json). Do not count `56.txt` and `56.bin` as distinct hash candidates.

**Original-signed-message algorithm audit (six pinned archive copies).** The six historical 2014 clearsigned messages enumerated in the frozen manifest (`2014-01-final-message`, `2014-01-liber-primus-hash-block`, `2014-01-onion-welcome`, `2014-01-onion5-liber-primus`, `2014-01-opening-book-code`, and `2014-05-liber-primus-release`, all `.asc`) each has an OpenPGP `Hash: SHA1` armor header and **none contains the 128-digit AN END digest** or names SHA-512/BLAKE as its target algorithm. ## P55 output-contract decision from p56/p57 and Stage11 (Director #490)

**Decision: no unique p55 output format is justified by the surviving original-source context.** Keep p55 as unknown plaintext until its 76 runes are decoded. Do not impose a Tor-address, URL, page-number, 64-byte preimage, SHA-512, or page-59 constraint on the decoder.

### What the adjacent solved pages actually require

The accepted p56 plaintext is headed **AN END** and says, in substance, that a page exists *within the deep web* which hashes to the printed **128-hex-character / 64-byte target**, and that pilgrims should seek out that page. The wording refers to **a page** as an external object; it does not say that p55 itself is the page, that p55 must be the page's raw preimage, or that the immediately preceding page must encode a URL. It supplies no digest algorithm, target hostname, canonical byte serialization, page MIME type, URL length, or address alphabet. A 64-byte target does not uniquely identify SHA-512. The six pinned 2014 clear-signed messages and the broader 18-message 2012–2014 archive have OpenPGP Hash: SHA1 headers; those describe PGP signature hashing, not the page digest.

The p57 **PARABLE** text says, in substance, “like the instar tunneling to the surface,” followed by shedding circumferences and finding divinity within. The same three clauses occur in the original 2013 761.MP3 ID3v2.3 TXXX frame, with its own punctuation and literal backslash-n separators. That is genuine earlier source context for the parable, but it supplies no address syntax, URL length, encoding, filename, digest family, or p55 output grammar. The p56 and p57 decoded texts are preserved as participant transcriptions of the original page images; the p57 TXXX carrier is a byte-audited original 2013 artifact.

### P55-derived candidates are not an output contract

The existing p55 FOLD route applies the conditional 2016 page/word map and reports the reversed solved-endpoint phrase **THE DEEP END**. This is a navigation/mnemonic candidate, not a recovered p55 plaintext: it selects only solved endpoints after observing the routes, the reverse ordering is an interpretive convention rather than a signed instruction, and the same three-word sequence occurs as a substring on p4. It may be a useful clue about the external “deep end,” but it does not prove a Tor address or a page pointer. See [the p55 FOLD endpoint report](p55-fold-solved-endpoint-phrase.md) and the [2016 map source](lp2-2016-signed-message-base58-word-map.md).

The literal p57-to-p55 crib is separately rejected: p55 has 17 printed words with lengths including 1 and 13, while the 20-word p57 parable has neither length; none of the four consecutive 17-word p57 windows matches the complete p55 word shape. This excludes only direct word-boundary-preserving reuse of p57, not a different plaintext or cipher. See [the complete word-shape gate](p55-p57-instar-literal-wordshape-crib-gate.md).

### Contract for the remaining decoder

The only source-backed downstream requirement is: **after p55 is decoded, use whatever explicit locator/instruction it actually contains, if any, to identify a separate deep-web page; then compare the exact candidate page bytes against the p56 target using an independently established digest algorithm and serialization.** A readable clue or locator is plausible; a v2 onion address, a URL, a page pointer, and a raw hash preimage are all unselected alternatives. The p55 fold phrase is not sufficient to choose among them. The correct current acceptance criterion for #41 is a complete, reproducible 76-rune p55 plaintext with original word boundaries, not a guessed output grammar. If the recovered text itself explicitly specifies an address, file format, digest or serialization, that new source instruction can then narrow the target-page test.
