### Pre-LP2 2013 Tor crawl custody leads (added 15 November 2026)

Two documented 2013 Tor content crawls are additional, lower-priority custody leads for the p56 page target. They are not public page archives in the cited records, and neither is known to contain Cicada material.

**TNO / Spitters et al., December 2013.** The study reports 5,725 known hidden services, 1,481 with downloaded content, 2,196,410 downloaded page URLs, and 324,623 pages with usable content after preprocessing. The paper's historical corpus downloaded HTML only; preprocessing filtered error/redirect pages, extracted text, and discarded texts shorter than 15 words. The paper itself does not establish whether original HTML or raw HTTP response bodies were retained, and the TNO repository record exposes the publication rather than a dataset download.

- Paper: https://gwern.net/doc/darknet-market/2014-spitters.pdf (DOI 10.1109/JISIC.2014.40)
- TNO record: https://repository.tno.nl/SingleDoc?docId=82829

**Current TNO/CFLW Dark Web Monitor (DWM), operator-gated route strengthened 19 November 2026.** DWM is the continuing commercial service associated with the TNO crawler, now operated by CFLW. Its own [history page](https://cflw.com/dwm/) dates TNO work to 2013 and describes the present service as a historical "wayback machine"; CFLW currently offers a two-week test plan and API access on its Premium plan. A 2025 peer-reviewed study states that DWM has accumulated 16 million domains and one billion pages over 11 years since 2013 and points researchers to CFLW for data access (Hartel, Junger & van Staalduinen, https://doi.org/10.1186/s40163-025-00246-w). A 2023 study of the crawler says raw data are archived in cloud storage and reports about 25 TB through the first half of 2022 (Oosthoek et al., https://doi.org/10.1109/ACCESS.2023.3235409). DarkDiff states that the crawlers retain each unique version of a page and that DWM has collected onion pages since 2013 (Hartel et al., arXiv:2308.12134; source code DOI https://doi.org/10.5281/zenodo.8050938). An INTERPOL-linked report describes DWM as providing access to all crawled and timestamped HTML pages, and another operational guide explicitly notes access to page source HTML. These facts make exact historical content substantially more plausible than the 2013 publication record alone. They still do not prove that the p56 target service entered DWM's crawl frontier or that original HTTP transfer bytes survive.

A second, more actionable property is now documented. The 2023 crawler study says full-match duplicate suppression uses both the front-page title and page source via a **hash generated at crawler runtime**. This creates a cheap first query for CFLW: identify the native hash algorithm and stored input representation, then compare the exact p56 512-bit target directly against any retained historical digest field before exporting page bodies. If the native digest is a different width or representation, the same archive still appears to preserve page source versions that can be tested in place. The current public literature does not identify the runtime hash algorithm, byte encoding, or whether that historical digest field is still queryable.

A 2024 TU Delft thesis completed with CFLW supervision makes the retained-object and query model more concrete. It says that on every successful HTML download DWM **stores the HTML file as a snapshot**, compares it with the previous download, and creates a **new version** when content changes; the crawler recursively discovers domains by snowballing. The same thesis states that DWM has a JSON:API interface able to list domains, obtain domain details, **list pages for a specified domain**, and retrieve extracted cryptocurrency/PGP/email records. The domain-list API includes `DiscoveredAt`, page count, inbound-domain and outbound-domain counts plus discovery-date filtering. Its research dataset spans September 2018 through January 2024, so this document demonstrates the current versioned-page/API architecture but does **not** establish that 2014 snapshots survived into the accessible tier. Source: Vyshnavi Molakala Narasimhalu, *Probing the Dark Web* (TU Delft, 2024), §4.1.1–4.1.2.

**Causal value and priority.** The p56 pointer is external by construction, and the preserved onion7 index terminates after the 58 book images with no next-address link. A useful archive therefore has to have discovered the target service independently. DWM is the strongest current custody route because it began crawling before LP2, recursively discovers new onion domains from page trees, retains unique historical page versions, and has a live operator with access controls. The same snowballing design is also its weakest assumption: an unlinked target service could have escaped the crawl. EURECOM/Deusto remains a high-priority separate route for exact response metadata because its 2016 study documented HTML and HTTP headers; DUTA and Moore–Rid remain distinct custody routes. A DWM hit is decisive only when the exact hashed representation is identified.

In particular, a historical DWM capture of `ky2khlqdf7qdznac.onion` can be compared against the independently preserved LP2 index/page material to determine whether DWM's stored HTML is byte-faithful or normalized. A target-digest miss has substantially less evidentiary force if DWM captured none of the known campaign services; multiple contemporary campaign hits would demonstrate that the crawler reached the relevant 2014 Tor neighborhood, though they still would not prove discovery of an unlinked target service.

**Hash-family discipline.** The repository's stronger source-provenance gate above remains controlling: the p56 page names no algorithm; all 16 pinned authenticated Cicada clear-signatures from 2012–2016 use `Hash: SHA1`, and the first pinned `Hash: SHA512` header is from 2017. Therefore neither SHA-512 nor Whirlpool is authenticated for p56. Period chronology only constrains plausibility: SHA-512 and Whirlpool existed before LP2, while standardized SHA3-512 postdates the 2014 release. The native DWM duplicate hash takes operational priority because it may permit an indexed exact-target lookup without selecting a page representation after seeing the target.
