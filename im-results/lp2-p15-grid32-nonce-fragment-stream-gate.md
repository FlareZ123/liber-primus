# P15-to-grid and grid-to-fragment cryptographic receivers: exact original negatives

**Agent8, 16 November 2026.** The authentic artifact gives an unusually compact *three-input receiver hypothesis*: sixteen printed p15 Fibonacci-prime-square numbers can be serialized as a **32-byte** candidate key; the **32×8** table printed on pp49–51 supplies exactly **32 eight-byte nonces**; and **31 thirteen-dot markers** divide the complete 58-page rune tape into **32 ordered fragments**. This three-way dimensional fit is exact. It supplies an executable original-source construction, but **no first-party sentence binds these objects into a stream-cipher instruction**. Two distinct recipients were therefore tested in bounded direct forms: using the grid as *nonces for rune text*, and using the grid as *256 bytes of ciphertext*. Neither produced unknown plaintext.

The experiment avoids fitting keys or nonces to ciphertext. Four source-root key serializations are locked: the p15 sixteen original square integers in printed row-major or clockwise spiral order, each encoded as unsigned 16-bit big or little endian. Every byte comes directly from the original p15 numerical source. Each row of the original corrected p49–51 sexagesimal table is the complete fixed eight-byte nonce for the correspondingly numbered interval. The two simultaneous p7 thirteen-dot markers and the empty p15 leading interval produce **two zero-rune fragments at indices 8 and 11**, retained in nonce numbering. The first **28** intervals contain exactly the original **12,956 unknown ciphertext runes**; the final four contain the solved tail. The original unknown-byte-index SHA-256 is `73473a68c3fc4296f16009716d7fee18c9c102173e6e70d090c9494cc5bd9252`.

The two chosen unframed standard streams each use a 256-bit key and eight-byte nonce at a zero-based stream counter: original **ChaCha20** with 64-bit counter and nonce, and **Salsa20/20**. Salsa20/20 is tested against the published 64-byte all-zero key/nonce reference vector `9a97f65b9b4c721b960a672145fca8d4...`; the standalone CJS tests the entire 64-byte vector. Neither stream was synthesized by fitting original ciphertext. Each cipher has **4 fixed key serializations × 3 proposed GP rune transports × 2 cipher signs = 24** full programs, or **48 original candidates** in total. The three rune transports are (i) mod29 additive pad, (ii) cyclic predecessor-exclusion mod28 and (iii) ordered predecessor-exclusion mod28. The latter two conditionally interpret an equal ciphertext predecessor as the EA rune, carry the first ciphertext glyph unchanged as an interval IV, and skip a key byte on each repeat. That rank28 exception is an inference from original scarcity of adjacent duplicates, not an authenticated encoding instruction.

None of the **48** exact source-derived programs produces recognizable English on the original opening or either untouched visual chapter. The highest training ChaCha20 selection also deteriorates on both independent original chapters. Each of the **six** cipher×transport positive-control configurations exactly encrypts and recovers **12,956/12,956 GP-English runes** under the independently selected row-major big-endian p15 key, authentic 32 row nonces and real 28 intervals. The original inputs also pass byte-exact re-encryption across all 48 tested programs. Correct roundtrips are implementation checks rather than evidence of a real LP2 key.

## Distinct recipient: decrypt the original table itself as 256 ciphertext bytes

The same exact p15 32-byte key could instead act directly on the original **256-byte grid** as a binary ciphertext packet. A historical **2014 OpenPuff password A=`33011033`** is independent of LP2 ciphertext and has exactly eight ASCII bytes; the reversed printed **1033|3301** also gives eight ASCII bytes `10333301`. Both are frozen as candidate original 64-bit stream nonces, which are byte-for-byte distinct from the table rows used above. We do not infer that an OpenPuff password is automatically a Salsa/ChaCha nonce.

[Original 256-byte Salsa20/ChaCha20 SFT](../sims/lp2_p15_33011033_grid256_salsa_chacha_sft.cjs) and [successful Windows Node22 run 43840084188](https://github.com/FlareZ123/liber-primus/actions/runs/43840084188) cover all four p15 uint16 source key serializations × both eight-character source nonce readings × the two 2014-era stream ciphers = **16** exact programs. The best decoded binary candidate contains only **113/256 printable ASCII bytes**; every output contains invalid UTF-8 and fails tested offset-zero signatures for GZIP, bzip2, XZ, ZIP, PDF, PNG, GIF, SQLite, ELF and 7z. None consists entirely of 0..28 GP rune bytes: the best GP29-byte count is far below 256. Every source candidate encrypts back to the exact original grid and passes a separate 256-byte planted binary roundtrip. A source-independent Salsa20/20 zero-vector also passes.

A simpler block-cipher receiver needs no independent nonce: **AES-256** directly decrypting 256 original grid bytes with the four source p15 keys. [Complete AES-256 original-source CJS](../sims/lp2_p15_aes256_grid256_direct_sft.cjs) and [successful Windows Node22 run 43840477247](https://github.com/FlareZ123/liber-primus/actions/runs/43840477247) cover three conventional direct modes: ECB, zero-IV CBC and zero-IV CTR, 4×3=**12** fixed original programs. All inputs and outputs are 256 bytes; their original-grid SHA-256 is `3b9b07d9a26e6d55c432d94d2661fdff3c2b348daed06821f2bdb23184a4b290`. Across all 12, **zero valid UTF-8 messages**, **zero recognized zero-offset container/file signatures**, maximum **118/256 printable ASCII**, and no GP29 byte-only candidate. Each mode passes an independent 256/256 binary plant and exact original-ciphertext re-encryption. A nonzero nonce, unadvertised IV, later container encoding or wholly different cipher is outside this finite family.

**The direct-grid interpretation therefore has 28 additional exact negative consumers**. Together with the 48 fragment-text programs above, the project now has a reproducible **76-program source-object join gate**, with the crucial distinction between *nonce*, *ciphertext*, *key* and *segment* roles retained. The original dimensions alone do not provide a first-party role-selection instruction, and none of these direct tests creates authentic unknown plaintext.

- [Salsa20/20 complete single-file CJS](../sims/lp2_p15_grid32_fragment_salsa20_sft.cjs), successful **Windows Node22** [run 43839306130](https://github.com/FlareZ123/liber-primus/actions/runs/43839306130), with source-independent 64-byte reference-vector assertion and correct original GP label display.

**Decision:** The three physical dimensions genuinely match a compact historical key/nonce/fragment architecture, which is more directly motivated than a random key sweep. The 48 fragment-text decryptions fail to yield original plaintext, and the 28 direct-grid decipherments fail to reveal a recognizable binary packet or GP29 payload. A future test should require an authored instruction selecting a stream, nonce row order or GP codec, or a distinct original-source artifact supplying such a selector. Arbitrary additional key hashes, nonlinear maps and counter offsets can generate limitless explainable ciphertext fits with no progress toward authentic plaintext. None is justified by the size match alone.
