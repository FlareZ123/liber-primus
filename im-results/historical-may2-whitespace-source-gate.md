# Pre-LP2 prime records and the 2014 May-2 whitespace handoff

**Evidence classification:** exact source-script inspection, a source-frozen original-cipher negative, and a cross-repository byte-provenance audit. **No independently authenticated May-2 trailing-whitespace key, recovered unknown LP2 plaintext, historical key, or genuine cipher.** This addresses [Director Issue #10](https://github.com/FlareZ123/liber-primus/issues/10) and [Director Issue #81](https://github.com/FlareZ123/liber-primus/issues/81), and supplements [the historical handoff](../workplace/historical-solve-path-to-original-lp2.md).

## Source findings and their effect on the key search

A historical **telnet-service** transcript has been reported to omit the primes 73–1223. That service's remote implementation need not be the same as the published 2013 bootable ISO script. The recovered [2013 ISO source script prime_echo](https://github.com/neuroretransmit/cicada/blob/main/2013/002-3301/rootfs-contents/usr/local/bin/prime_echo) (Git blob SHA-1 **65a569cf1b3eecb0f7c17ffc569a54ed8ecdf649**) actually prints **all 464 primes from 2 to 3301** in ascending order, exactly once. An executable parse of each echo statement finds **zero omissions, duplicates, nonprime numbers or reordered values**. Values 73, 79, 83, …, 1223 explicitly appear. Hence the telnet missing-prime sequence is **not an omission specified by this local ISO script**. This does **not** falsify a separate, historically different telnet service or its reported transcript. Treat the remote telnet observation as an unverified but distinct source unless independently captured original server bytes or source code establish it. The report is nevertheless structurally informative: the alleged missing run is **exactly primes #21–#200**, comprising **18 entire ten-prime rows** under the original ISO script's every-tenth-prime line break. The visible boundary values are **71 (#20)** and **1229 (#201)**. The remote transcript also reports extra spaces at **29→31 (#10→#11)** and **3257→3259 (#460→#461)**, two more ten-row boundaries of that script. Missing screen lines or a copied/truncated terminal chunk is therefore a concrete alternative explanation for the 180-value gap, while an intentionally edited remote-service output remains possible. This aligns sources without asserting that the two historical programs were identical. Contemporary telnet bytes/code are needed to adjudicate that distinction. It has no support from this recovered source.

The repository's [archived 2 May 2014 clearsigned reply](../resources/cicada2014-may2-signed-message.asc) has eleven ordered whitespace-run counts **2,3,5,7,11,13,17,23,29,31,37**, corresponding to the first twelve primes **with 19 omitted**. The **5** before the onion address is leading indentation. The other **ten** counts occur as trailing spaces or whitespace-only lines. As explicitly specified in the historically applicable [OpenPGP RFC 4880 §7](https://datatracker.ietf.org/doc/html/rfc4880#section-7), cleartext signatures remove trailing spaces and tabs before signing; see also [RFC 9580 §7.1](https://www.rfc-editor.org/rfc/rfc9580.html#section-7.1). Thus the PGP signature can authenticate the nontrailing text and the leading five spaces, **while it cannot authenticate the other ten run lengths**. An independently captured contemporaneous byte stream would be required to establish those counts as authentic key material. The absence of 19 does not independently prescribe a key schedule or cipher operation.

**Direct archive disagreement:** the [Michel Oosterhof archived reply](https://github.com/micheloosterhof/cicada-2014/blob/master/stage11/message.txt.asc) preserves the exact eleven-value series above, while the [neuroretransmit archived reply](https://github.com/neuroretransmit/cicada/blob/main/2014/010-hidden-service-reply/message.txt.asc) contains **2,3,5,6,11,13,17,22,29,31,37**. The fourth and eighth entries differ (**7→6, 23→22**), both at trailing-space positions. The two files have **byte-identical nontrailing signed body text after OpenPGP whitespace canonicalization and identical base64-armored signature contents**. A separate whitespace-only separator before the message header and whitespace inside the armor also differ. Thus two surviving archives present incompatible numerical “keys” while presenting the same cryptographically signed message, an independent concrete demonstration of signature noncoverage. Their signatures' cryptographic validity was not freshly rerun in this experiment; the key-independence conclusion follows from the standard and the exact archived body/signature comparison.

**Cross-repository byte-provenance audit (2026-11-11):** the apparent number of copies is much larger than the number of independent byte witnesses. The decisive Git-history result is in Michel Oosterhof's 2014 repository:

It has the five leading spaces before the onion address, but **no trailing-space runs and no whitespace-only runs**.
- Commit [`5431b03e`](https://github.com/micheloosterhof/cicada-2014/commit/5431b03eacf15d27c5f02eae860efcfdb7f1917b), **2014-05-13 20:55:55 UTC**, titled **“preserve spaces”**, modifies that same file to **1,183 bytes**, blob SHA-1 `e2b7382ac2cfb0adfe028cc063fc6048e0ad718e`. The commit is contemporaneous and predates the later prime-sequence interpretation, but the repository does not record the original upload, an HTTP capture, or another independent witness from which the added bytes were restored. The article and repository do not publish a contemporaneous raw upload, server-side file hash, or byte-preserving request log. This is a valuable independent-recipient lead, but the public artifact is a later normalized copy, not the required byte-level witness.

**Decision for Director Issue #81:** no independent pre-interpretation, byte-preserving witness fixing the trailing-space bytes was recovered. The only 2014 Git revision containing the 7/23 pattern is Michel's May-13 “preserve spaces” commit; all later exact 7/23 mirrors found here share its blob, while the later alternatives disagree or normalize the spaces. The signature cannot authenticate the difference. Therefore **retire the May-2 whitespace-as-key route**: do not use 7/23, 6/22, or missing-19 as LP2 key material, and do not run further prime-gap key transfers. Reopen only if an independent recipient's raw 2014 upload or a recovered Wayback/Pastebin body is supplied with capture time, exact bytes, and verifiable provenance.

**Contemporaneous seventh-onion witness (Director Issue #25):** Michel Oosterhof's repository records commit `6c3421a4d245596e403c88e037509d162a2afd17` at **2014-05-11 18:33:43 UTC**. That single commit adds `stage11/message.txt.asc`, `stage11/ky2khlqdf7qdznac.onion/index.html`, and all 58 JPEGs. The 1,640-byte index is byte-identical to `resources/cicada2014-onion7-index.html`: its only content is title `133`, container id `331`, and image references `0.jpg`–`57.jpg` in order. The 58 image Git-blob SHAs and byte sizes match the current canonical LP2 images `resources/liber-primus/17.jpg`–`74.jpg` exactly. The commit therefore supplies a contemporary participant mirror of the delivery page and assets, but not the original HTTP response or response headers. No non-image link, script, form, comment, instruction, or continuation appears in the preserved page body. The original server response/headers are the specific missing artifact; the available contemporary body is sufficient to conclude that this surviving delivery page itself contributes no actionable LP2 cipher/key selector. This does not assign any meaning to `133` or `331`.


## Executed original-LP2 test

Earlier Cicada phases used GP-index Vigenere and prime-totient shifts. To test the eleven historical values without searching arbitrary keys, the [single-file CommonJS reproducer](../sims/may2_historical_source_gate.cjs) freezes their visual order and forms three natural direct **periodic GP29 subtraction keys**: each prime minus one, its canonical GP prime index, or prime modulo 29. It also tests the competing first eleven *consecutive* primes (with 19 restored) under the prime-minus-one rule.

For each key, the frozen decoder reads original physical **LP2 page 0, 262 runes**, with key clock reset at the page beginning. It exhausts all **16,384** possible masks of the 14 literal/nonconsuming ciphertext F symbols (65,536 original-input decodings across four keys). It scores using an independently trained GP trigram of Gibran's *The Prophet* and compares against all **62,435** complete equal-length windows of the same source.

| Key derivation | Best original p0 score, nats/rune | Best F mask |
| --- | ---: | ---: |
| Historical 11 primes, prime minus 1 | **−5.661101** | 13416 |
| Historical 11 primes, GP index | **−5.639080** | 1728 |
| Historical 11 primes, residue mod29 | **−5.346064** | 14542 |
| Competing first 11 primes including 19, prime minus 1 | **−5.803807** | 4416 |

The untreated original p0 scores **−6.275811**. The worst independent literary window scores **−2.394686**, median **−2.080088**: **zero of 62,435** natural-GP windows have scores as poor as any of these maximally fitted decryptions. The outputs contain no readable native-GP English. This is a bounded exclusion of **these particular four direct GP29 periodic subtractions** with every observable F skip mask. It does not exclude an independently indicated nonlinear state, a different textual register, another word segmentation, or a separate source-locked mechanism.

## Remaining dependency

The first obstacle is a **byte-authentic 2014 HTTP capture** of the May-2 response before it was recopied and normalized; its signed content cannot certify the trailing-space counts. The second and larger obstacle is a **contemporary instruction that determines a concrete LP2 cipher, key extraction, clock, state and starting register from those sources**. The existing publicly recovered Cicada chain delivers the 58 scans without fixing that operation. The local ISO full prime sequence does not authenticate the reported remote-telnet omission, and the mostly unsigned 11-run whitespace pattern presently cannot serve as an identified original key.
