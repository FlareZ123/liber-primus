This is a small partial-key + independently testable crib chain; it does not demonstrate that a hidden historical key file was necessary. Proposed next edge: use that intermediate in a typed receiver for the adjacent p16–22 rune passage. The exact source-fixed direct Hill, progressive spiral/prime clock, plain Fibonacci-autokey and lifting interpretations are already rejected or unselected; a new arbitrary receiver cannot distinguish self-containment from missing instructions. **B — authenticated external continuation.** Start with the preserved original signed 2014 Stage11 location message. Its executable first operation is the already-authenticated signature verification followed by parsing its explicit onion location and original index of 58 images. The recognizable output is the original LP2 artifact set, independent of any unknown rune plaintext. A distinct hypothesized second delivery would then provide a typed key/receiver instruction or participant-held operand used on that set. The known message ends at the collection's location; it does not contain the proposed second delivery. The 2016 signed coda confirms the book as the navigation subject and the OpenPGP identity but does not add a key, state or recipient-specific operand.

A **specific missing artifact** would distinguish the proposed rival dependency: a first-party post-Stage11 continuation, authenticated to the original key, explicitly identifying the LP2 target interval and a required delivered operand or describing a self-contained internal producer/consumer. If it specifies an indispensable external secret, Graph A's proposed self-contained receiver is insufficient; if it explicitly defines an internal producer/consumer with no external input, Graph B's hypothesized key delivery is unnecessary for that receiver. Mere recovery of another historical payload, an unsigned solver claim, or a repeated prime is not this artifact. No evidence is claimed that such a continuation ever existed.

## Cheapest decision test, existing original-input constraints, and fork

The actual p15 arithmetic validation is already passed; direct consumption of that intermediate is already extensively tested, including the original p16–22 window. The alternative claim that another typed key object is simply embedded in the original p49–51 table in the surviving book has exact existing counterexamples: all 256 cells are shared by two byte codebooks, so uniform bytes have identical likelihood under either; direct cellwise and whole-field base60 OpenPGP reads fail mandatory packet syntax. See [radix identifiability](lp2-p50-radix-codebook-overlap-source-gate.md) and [typed packet rejection](lp2-p50-wholefield-base60-openpgp-gate.md). The already-recovered 2013 Parable checksum independently validates the known p57 only, not an unknown chapter ([typed checksum decision](lp2-2013-instar-structured-operand-decision.md)).

Therefore the cheapest remaining discriminating experiment is conditional on the missing artifact or a genuinely new internal selector: freeze its operand type, receiver interval, representation and state update; validate the producer by a non-language check; apply the receiver only to its named target and hold out the independent continuation. Do not repeat a known direct consumer, general PGP/byte scan, old square upload or source-phrase search. No new original-input run is feasible that discriminates these two graphs as specified, since neither missing edge is present in the source set; the already-completed exact original checks are cited instead. A failure of one arbitrary decoder is not evidence for external key delivery.

This completes the bounded dependency decision via the specific-missing-artifact fork. The next priority is a typed edge from an independently recognizable producer to an original unknown-page receiver, not a broader list of possible keys. No unknown plaintext, key, cipher, or destination is claimed.

## Independent intermediate-marker transfer: mixed-digit Stage04 identifier (#3058, Agent8, 26 November)

The authenticated historical Stage04 small image contains 18 Gematria Primus (GP) runes and two literal decimal digits, `5` and `3`, embedded in one uninterrupted 20-symbol identifier. The archived receiver is the fourth onion host. With the clue-derived key phrase `WELCOME PILGRIM TO THE`, correct GP tokenization (including `TH` as one rune) yields 18 key shifts:

`[7,18,20,5,3,19,18,13,10,20,6,4,10,19,16,3,2,18]`.

The digits are **literal payload symbols that do not consume the key clock**. Their exact state trace is:

| Cipher symbol position | Literal digit | Rune symbols consumed before | Next key shift (1-based) | Rune symbols consumed after |
|---:|---:|---:|---:|---:|
| 9 | 5 | 8 | 10 | 8 |
| 15 | 3 | 13 | 19 | 13 |

Thus the first digit is emitted unchanged after eight rune decryptions; the ninth rune still uses shift 10. The second digit is emitted unchanged after thirteen rune decryptions; the fourteenth rune still uses shift 19. At the end, exactly 18 key symbols have been consumed and the original `5` and `3` remain in the output. The unique exact normalized host branch is `AUOWYFGL5LKZFJ3NONION`, matching the archived `avowyfgl5lkzfj3n.onion` after the archive's documented U/V and dot normalization. Wrong-key and wrong-direction controls do not match. Eight of the sixteen transliteration branches satisfy the 16-base32-character + `ONION` shape; the exact archived host is one branch.

A source-code caveat matters: the archive's original `key_to_shifts()` peeks ahead for digraphs but does not consume the second letter, so it counts `TH` twice and produces 19 shifts. The corrected GP-token serialization consumes `TH` as one symbol and produces the 18-shift sequence above. The digit-clock result is tested with this corrected, alphabetically faithful GP serialization; the old implementation bug is not silently treated as the intended key schedule.

The complete source-pinned replay is in [the existing reproduction script](../sims/stage04_small_image_vigenere_repro.cjs), which records the original `neuroretransmit/cicada` commit and source image/transcription blob IDs. It reproduces the archived receiver without contacting the historical endpoint.

### LP2 candidate test

The LP2 original images do **not** reproduce the historical operand grammar:

- **p10, original `resources/liber-primus/27.jpg`:** the isolated `7` is visually bounded by dot punctuation on both sides. It is not embedded in an uninterrupted rune/decimal identifier like the Stage04 `...ᚱ5ᚢ...ᛝ3ᛠ...` source.
- **p36–38, original `resources/liber-primus/53.jpg`, `54.jpg`, `55.jpg`:** the red numerals `1`–`5` are paragraph/list labels at the left margin, not symbols in the rune stream.
- **p15 and pp49–51:** these are separate numerical tables, not mixed rune/decimal identifiers.

I therefore froze the only superficially adjacent candidate, p10's `7`, and tested its *source-visible operand grammar* before any receiver experiment. It fails the historical match condition because the punctuation delimits it from the rune stream. Applying the Stage04 non-consuming rule anyway would require deleting the dots or inventing a larger operand window. The p36–38 labels are plainly numbering, not state events. The p10 `7G` password interpretation is already independently tested and negative.

**Decision:** the Stage04 source establishes one narrow historical rule—literal decimal characters embedded in a continuous encrypted identifier can pass through without advancing a rune-key clock. It does not establish a general rule for standalone numerals or list labels. No LP2 event matches the exact operand grammar, so no key clock or receiver decode is selected. Retire this transfer; no new LP2 plaintext, key, or cipher follows.
