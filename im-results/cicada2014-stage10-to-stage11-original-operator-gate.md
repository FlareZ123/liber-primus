# Cicada 2014 Stage7→Stage11: qualification, callback and LP2 release

**Original technical audit:** Agent33, 22 November 2026. **Chronology update:** Agent11, 26 November 2026 (Director #3013). The supported sequence is a qualification and distribution path, not an LP2 decryption operation. Stage7 yields the 99 magic-square values later requested by Stage10; Stage10 asks the solver to submit them and provide a participant-operated Tor endpoint and GnuPG public key; Stage11 points to Cicada's next onion; the archived index serves 58 static LP2 images. The only preserved participant-uploaded message is a separately signed copy of the same canonical Stage11 redirect. A distinct participant's **contemporary first-person April 2014 report confirms they submitted their Tor endpoint and were receiving periodic visits**, but it does not identify a Cicada visitor, the endpoint URL, a POST receipt, or an encrypted operand. No surviving public artifact contains a recipient-linked encrypted reply or a GP29 decryption operand.

The extracted text is preserved as [a derived resource](../resources/cicada2014-openpuff-magic-squares.txt); the [2014 fifth-onion README](https://github.com/cicada-solvers/neuroretransmit-cicada/blob/b13600373d3400d75ec4208198019f3d92a304dd/2014/007-fifth-onion/README.md) explicitly says their use was then unknown. Separately, it tells the participant to operate a Tor hidden service, serve their GnuPG public key at /key.asc, and expose /cgi-bin/upload with a file field. This is a participant-side service contract, not a specified GP29 cipher operation.

3. **Archived 13 February 2014 — Stage10 response witness.** The preserved [152-byte response](../resources/external/2014-stage10-post-square-response.html) thanks the participant and links /107.jpg, /167.jpg, and /229.jpg. The three square values and field schema are nevertheless recoverable from Stage7 and the signed Stage10 form.

4. **2 April 2014, 08:49:51 UTC — Stage11 redirect.** The [Cicada-signed message](../resources/historical/cicada2014-stage11-message.asc) points to ky2khlqdf7qdznac.onion. This is Cicada's next-stage onion, not the participant's personal onion service.

5. **2 May 2014 — participant callback report.** The [participant archive](https://github.com/neuroretransmit/cicada/blob/ade9a02889ef8acbc8cde8edbfd0a785c369f4c3/2014/010-hidden-service-reply/README.md) reports Cicada requests for /key.asc, /, and POST /cgi-bin/upload, each returning HTTP 200. 6. **11 May 2014, 18:33:43 UTC — archived Stage11 index.** The [original static index](../resources/historical/cicada2014-onion7-original-index.html) contains 58 ordered image references, 0.jpg–57.jpg, and no scripts, forms, input fields, key material or cipher implementation. The timestamp is the preserved archive commit time, not independently established first-serving time. The 58 images are the LP2 release; p0–p55 are the 56 unsolved pages, while p56–p57 are the later solved/closing pages.

### Single prioritized missing input

The only remaining archival object worth prioritizing is a **byte-preserving participant-side capture of the 2 May callback transaction**: the participant onion URL, the exact bytes/fingerprint served at /key.asc, Cicada's complete raw multipart POST /cgi-bin/upload body, and the participant CGI response. This single transaction record could establish whether any individualized encrypted material accompanied the generic signed file. If no complete callback capture exists, retire Stage10→Stage11 as a key source and classify it as qualification/distribution only. The missing Stage10 /cgi-bin/squares request/handler is a lower-priority archival gap; the inputs and static LP1 response are already understood, and it supplies no evidenced LP2 decryptor.

## Reconstructed intended player operation from original first-party materials

The [two independently archived Stage10 HTML copies](https://github.com/krisyotam/cicada3301/blob/main/puzzles/2014/assets/stage10/ut3qtzbrvs7dtvzp.onion/index.html) in `krisyotam/cicada3301` and `micheloosterhof/cicada-2014` have identical Git blob SHA1 `9d7c35bc8fff24c8079668c9d070d98277502f7c` and 1943 original LF bytes, which are now preserved in [this repo](../resources/historical/cicada2014-stage10-original-form.html). It includes the following **actual, concrete, user-visible protocol** inside the PGP-signed part of the page:

1. Submit the three separately solved historical magic squares as named CGI form fields `53301` (5×5 row sum3301), `71033` (7×7 sum1033), and `51033` (5×5 sum1033), and provide the URL of one's own Tor hidden service in a field named `onion`. The page's literal HTML form is `method=post`, `action=/cgi-bin/squares`. The historical [actual solved squares](../resources/cicada2014-openpuff-magic-squares.txt) are first-party outputs of the preceding stage, rather than later guesses.
2. Host a participant-operated CGI at `/cgi-bin/upload`, accepting a binary upload in input named `file`, and expose a participant's GnuPG public key at `/key.asc`.
3. The signed text says **“We will contact you soon.”** The original webpage contains *no* JavaScript cipher code or inline key derivation; separate archived response witnesses are described below. The signed form specifies a participant-operated upload channel and public key, but no cipher transformation or encrypted reply is specified. The only preserved callback payload is a generic clear-signed redirect; actual use of the participant key for encryption is unproven.

### Client-side contract cross-witness decision (#2992, Agent4, 26 November)

The square form belongs to **Stage10**, whereas Stage11 is the subsequent 58-image release. A distinct archived [neuroretransmit form](https://github.com/neuroretransmit/cicada/blob/ade9a02889ef8acbc8cde8edbfd0a785c369f4c3/2014/008-sixth-onion/ut3qtzbrvs7dtvzp.onion.v2-form.html) is now preserved as [1940 LF bytes](../resources/historical/cicada2014-stage10-neuro-form.html), blob `6a7130783f73320a5e6e5f802061f7851071a349`. Compared to the 1943-byte witness, the only changes are three removed blank lines and a malformed closing paragraph tag (closing u instead of p) at the address label. The signed preformatted body is identical. Both documents have precisely one form, three empty textareas, two inputs (one unnamed submit), and the same four named controls in the same order. Neither contains script elements, linked non-image resources, event attributes, hidden controls, or a client-side magic-square validation rule. Both rely on ordinary browser form behavior and an unseen server-side interpretation; no exact accepted square serialization or server validation can be derived from them. The 1640-byte Stage11 index has 58 image references and zero forms/scripts. These are bounded archival observations, not a proof that unpreserved captures lacked additional material.

A second distinct archived [submission response](https://github.com/neuroretransmit/cicada/blob/ade9a02889ef8acbc8cde8edbfd0a785c369f4c3/2014/008-sixth-onion/ut3qtzbrvs7dtvzp.onion.v2-submitted.html) is preserved as [168 LF bytes](../resources/historical/cicada2014-stage10-neuro-submitted.html), blob `7aa12f62b78508ae32ee8508bc89683763dedc48`. This is a stronger source-grounded historical explanation for **where some first-party material could have been delivered**, compared with assigning a key to the coincidental length of an unrelated hex string. However, no source currently proves that that private exchange carried a later LP2 key. The stage protocol also predates the final 58-page LP2 release and need not have been intended to decrypt it.

## Stage10 public-key ownership and the actual May 2014 upload

The historical `/key.asc` address is **participant-relative**: the signed form requires the solver to *generate* a new GnuPG key pair and serve their **own public key** at `http://<participant's onion>/key.asc`. It does not name a Cicada-hosted key, an author-chosen shared secret, or a unique period byte sequence. The documented May 2 request sequence, `GET /key.asc` then `GET /` then `POST /cgi-bin/upload`, has historically recorded user agents `Cicada/33.01 CicaDOS 1.033 E Edition` and `Cicada/33.01 Cic/DOS/ 1.033 S Edition`; see [2014 participant-stage history](https://connortumbleson.com/2024/12/23/the-cicada-3301-mystery-puzzle-3-solve-part-4/) and [contemporary community logs](https://uncovering-cicada.fandom.com/wiki/Unresolved_(AFAIK)). The accounts support the *direction* of the cryptographic exchange, though the preserved log is a participant report, not a signed Cicada server log.

The authentic **Cicada** public verification key is a **different object**, preserved as [`cicada-3301-2012-public-key.asc`](../resources/historical/cicada-3301-2012-public-key.asc), key ID `7A35090F` / fingerprint `6D854CD7933322A601C3286D181F01E57A35090F`. It can authenticate purported instructions when paired with a valid signature; its **public** key material is not a decryption secret. The archived actual uploaded continuation [`cicada2014-stage11-message.asc`](../resources/historical/cicada2014-stage11-message.asc) is `BEGIN PGP SIGNED MESSAGE` with an openly readable `ky2khlqdf7qdznac.onion` pointer. It contains no `BEGIN PGP MESSAGE` ciphertext, session-key packet, GP29 mapping, LP2 key, IV, or cipher receiver. This means the recovered **public** handoff is one authenticated onward address, not a manuscript decryption handoff.

**Independent signature/whitespace audit (Agent5, 2026-11-23).** GPG verification of both the local Stage11 message and the separate upstream neuroretransmit/cicada copy at 2014/010-hidden-service-reply/message.txt.asc returns GOODSIG/VALIDSIG under Cicada fingerprint 6D854CD7933322A601C3286D181F01E57A35090F, timestamp **2014-04-02 08:49:51 UTC**. The signed v2 form at 2014/008-sixth-onion/ut3qtzbrvs7dtvzp.onion.v2-form.html.asc also verifies under the same key, timestamp **2014-01-25 08:26:57 UTC**.

The earlier wording that the local reply lacked five leading spaces was incorrect: both copies contain **five leading spaces** before ky2khlqdf7qdznac.onion, and those leading spaces are covered by the cleartext signature. The copies differ in trailing whitespace (six versus seven spaces after the onion address; 22 versus 23 after “Good luck.”) and whitespace-only lines. OpenPGP cleartext canonicalization strips trailing whitespace, so those varying counts are not authenticated. The cited scream314 hints_never_used.md is a community-maintained inventory, not an author-authenticated clue. Do not infer a prime-length key from those trailing runs; the only consistently authenticated indentation is the five-space prefix, for which no source-specified operation or LP2 receiver exists.

The separate neuroretransmit/cicada archive labels its 2014/008-sixth-onion/cgi/cgi.py as a mock CGI and cgi/key.asc as an example solver key, and explicitly says the mock was never used in the real puzzle. They are not the missing server backend or a Cicada secret. Its 2014/010-hidden-service-reply README reports GET/POST access logs and a May 2 distribution, but those logs are unsigned community evidence; the signed message timestamp is April 2. The participant archive's message.txt.asc is a separately signed copy of the public Stage11 redirect: its canonical text body is identical, its signature timestamp is the same 2014-04-02 08:49:51 UTC, and the signature verifies under Cicada's published key. It contains no PGP-encrypted MESSAGE block or recipient envelope. The single remaining archival gap is the complete participant-side callback transaction (participant URL, served /key.asc, raw multipart POST body and CGI response); only that record could show whether any additional individualized content accompanied the generic file. In its absence, there is no evidence of an LP2 key or decryption operand.
