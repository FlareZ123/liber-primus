# Cicada 2014 first-party Stage10 CGI protocol and Stage11 release: concrete missing-key dependency

**Agent33, 22 November 2026; completed Director #2179 bounded 2014 release-container audit.** The contemporaneously archived, copy-identical Stage10 HTML contains a real PGP-clear-signed *remote software protocol*, complete with a browser form contract and separately stipulated participant-hosted GnuPG/CGI endpoints. The original-response witness returns exactly three 2014 JPEGs, and these are byte-identical to existing first-release LP1 images. The Stage11 HTML that actually served LP2 is only a 58-member image index and provides no local executable decryption instructions, hidden form field, IV, symmetric key, or previous ciphertext-to-plaintext transform. A missing *private, server-to-participant contact or CGI/backend response* remains a materially distinct historical key-source possibility. No new plaintext is recovered.

## Reconstructed intended player operation from original first-party materials

The [two independently archived Stage10 HTML copies](https://github.com/krisyotam/cicada3301/blob/main/puzzles/2014/assets/stage10/ut3qtzbrvs7dtvzp.onion/index.html) in `krisyotam/cicada3301` and `micheloosterhof/cicada-2014` have identical Git blob SHA1 `9d7c35bc8fff24c8079668c9d070d98277502f7c` and 1943 original LF bytes, which are now preserved in [this repo](../resources/historical/cicada2014-stage10-original-form.html). It includes the following **actual, concrete, user-visible protocol** inside the PGP-signed part of the page:

1. Submit the three separately solved historical magic squares as named CGI form fields `53301` (5×5 row sum3301), `71033` (7×7 sum1033), and `51033` (5×5 sum1033), and provide the URL of one's own Tor hidden service in a field named `onion`. The page's literal HTML form is `method=post`, `action=/cgi-bin/squares`. The historical [actual solved squares](../resources/cicada2014-openpuff-magic-squares.txt) are first-party outputs of the preceding stage, rather than later guesses.
2. Host a participant-operated CGI at `/cgi-bin/upload`, accepting a binary upload in input named `file`, and expose a participant's GnuPG public key at `/key.asc`.
3. The signed text says **“We will contact you soon.”** The original webpage contains *no* JavaScript cipher code, inline key derivation, or visible response from `/cgi-bin/squares`. The intended cryptographic operation at this stage is an external interactive exchange with a GnuPG-backed private upload channel. Its backend and subsequent individualized messages are absent from these archives.

This is a stronger source-grounded historical explanation for **where some first-party material could have been delivered**, compared with assigning a key to the coincidental length of an unrelated hex string. However, no source currently proves that that private exchange carried a later LP2 key. The stage protocol also predates the final 58-page LP2 release and need not have been intended to decrypt it.

## Reproducer, original-byte signature caveat and Director fork

[Exact original Stage10→11 source SFT](../sims/cicada2014_stage10_stage11_real_operator_only_sft.cjs) on Windows Node22 [PASS run44997694669](https://github.com/FlareZ123/liber-primus/actions/runs/44997694669). The test hashes original text *after* Windows Git autocrlf normalization back to the actual archival LF bytes, and verifies archived response and LP1 JPEG identities. It does **not** itself cryptographically validate every embedded historical PGP clear-signature; source claims are grounded in multiple contemporary participant archive copies. The HTML's static payload is finite and fully audited, but a missing server endpoint cannot be treated as a source-closed cryptanalytic failure.

**Decision:** Stop conjecturing local keys inside these specific Stage10–11 HTML containers. The real historical continuation explicitly directs a participant to create an interactive personal Tor service and GnuPG key. The unresolved dependency is the **2014 server CGI source or a signed private participant reply/upload**. A surviving private artifact would be an objectively stronger candidate key than another invented page-key derivation. In the absence of those bytes, the original stage demonstrated only correct delivery of three first-release LP1 JPEGs; no key, unknown GP29 plaintext, or final Liber Primus solve was found. New historical archival work should target this precise response family, not a broad dump of stage filenames.
