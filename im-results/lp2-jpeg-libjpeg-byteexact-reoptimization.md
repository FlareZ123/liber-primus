# All LP2 JPEG compression bytes regenerate exactly from the quantized coefficients

**Agent8, 19 November 2026. Classification: exact original-file structural exclusion for independent JPEG Huffman/container payloads. No LP2 plaintext, key, or destination is recovered.**

## Question

The earlier JPEG census showed identical APP0/ICC structure and two component/quantization families, but the original LP2 files also contain **page-specific Huffman tables**. Every one of the 58 pages has a distinct complete DHT signature. Because Cicada previously used image-level hiding, those varying table bytes are a plausible file-artifact channel until their origin is explained.

The decisive test is whether an ordinary JPEG encoder can regenerate those bytes from the already-visible compressed image state.

## Coefficient-domain reconstruction

For every original `17.jpg` through `74.jpg`:

1. read the original JPEG header and **quantized DCT coefficient arrays** through the libjpeg API;
2. copy its critical JPEG parameters;
3. set `optimize_coding = TRUE`;
4. write the **same coefficient arrays** back through libjpeg without pixel decoding/re-encoding;
5. remove only the original APP2 ICC segment before comparison, because `jpeg_copy_critical_parameters` does not copy application metadata.

The runtime control used libjpeg-turbo 2.1.5 through the traditional libjpeg-compatible API. The official project documents this API compatibility and the coefficient-domain transcoding interfaces.

## Exact result

**58/58 LP2 pages match byte-for-byte after the identical ICC APP2 segment is removed. Zero bytes differ.**

This is stronger than matching decoded pixels or table statistics. The regenerated file reproduces, exactly:

- APP0/JFIF bytes;
- all DQT quantization-table segments;
- all per-page optimized DHT Huffman-table segments;
- SOF0 frame parameters;
- SOS scan parameters;
- the complete entropy-coded scan data through EOI.

For source scan17 / physical p0:

- original SHA-256: `197e1e153958b9a2736b09c10eea7d8bb00e0632fd22a8d9606840becc79942e`;
- after ICC removal: `b460559e21fe21beb14095a9449393af07620b8fd3c7e70497ae7f64288056e4`;
- regenerated bytes: **692,931**, exactly equal to that ICC-stripped original.

For source scan74 / physical p57:

- original SHA-256: `1dabc100ddbf1fc49715219636984eb6ad96a2bd8035e196c12e66db77a1077b`;
- after ICC removal: `e32731d6c501f9f9de10b7c7c91361f437a524a8e9c19e6b67a8ba64c618f5cf`;
- regenerated bytes: **315,482**, again exact.

The same exact equality holds for all intervening 56 pages.

## Cryptanalytic consequence

The varying Huffman tables are **not an independent metadata payload**. Standard optimized libjpeg coding regenerates them, and the entire entropy stream, deterministically from the original quantized coefficient arrays.

Combined with the existing container census:

- LP2 has no trailer payload;
- no per-page COM/APP metadata payload;
- the ICC profile is identical across all 58 pages;
- RGB/grayscale component mode is explained by visible production state;
- the remaining JPEG core bytes are exactly regenerated from the coefficients.

Therefore further JPEG-file analysis should target **quantized coefficient values themselves** only when an independently motivated steganographic operation exists. Re-searching DHT byte patterns, Huffman code lengths, entropy bytes, JFIF fields, or other compression serialization as separate key material would double-count deterministic encoding of the coefficient arrays.

This result does **not** exclude coefficient-level steganography. OutGuess and other coefficient-domain schemes operate precisely in the remaining channel, and they require their own authenticated extraction tests.

## Reproduction

Run:

`python sims/lp2_jpeg_libjpeg_reoptimization_sft.py`

Requirements are a C compiler and libjpeg development headers. The single-file SFT embeds the minimal coefficient-domain transcoder, compiles it in a temporary directory, processes all 58 originals, removes APP2 from each source byte stream, and requires byte-exact equality.

Local source execution on libjpeg-turbo 2.1.5: **58/58 exact, 0 mismatches**.
