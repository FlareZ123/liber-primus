## The source clue and frozen readout

The original terminal p55's last six GP ciphertext runes are exactly the same as p27 local indices 28–33, transcribed `DJUBEI`. The solved p56 opening `AE` equals p27 local index34; its next rune p27 index35 is `F`. Reading this exact eight-rune p27 span under canonical GP29 transliteration gives **`DJUBEIAEF`** (nine printed ASCII characters because `IA`/`AE` are GP digraphs). This is a plausible **candidate password** supplied by an actual cross-page comparison, and the contemporaneous 2014 puzzle used OutGuess. There is **no Cicada-authenticated instruction** selecting these eight runes or OutGuess rather than OpenPuff as a payload reader.

I froze one literal password, no case/key/phase variants, and the two original matching-artwork carriers: original archive 44.jpg (physical p27) and 72.jpg (physical p55). Historical OutGuess from fixed source commit `24810e14327c2bbeedeaadd3e24491f2a4425c02` ran under the repository's existing **manual** `.github/workflows/lp2-outguess.yml` with `custom_password=DJUBEIAEF`, `custom_image=44` or `72`. The runner first verified an authentic published positive from original 00.jpg/08.jpg and a real `-k 79` embedded-and-extracted 47-byte plant. It also tested a deterministic **known payload-free JPEG** with this same key. The workflow preserves every nonempty raw output even without a recognized format.

## Pairwise XOR, with one decisive wrong-password discriminator

The original source-pair's identical extracted 1,180-byte prefix and 1,339-byte suffix could conceivably cancel a reusable pad. One additional **fixed XOR operation** was therefore applied to the *whole original recovered byte arrays*, both for the p27/p55 source pair and for four pairings with the unrelated original controls. A pinned, read-only Node22 [source-bridge XOR SFT](../sims/lp2_p55_p27_outguess_crosscarrier_xor_sft.cjs) checks the exact independent source runes and all four original extraction SHA256 hashes, confirms a **56-byte authentic keyed native OutGuess plant**, and prints full reproducible pairwise statistics. It runs with the original maintained native extractor in [passing manual workflow 43710288877](https://github.com/FlareZ123/liber-primus/actions/runs/43710288877).

The source 44⊕72 output contains **3,485 zero bytes** total, including source-independent shared 1,180/1,339-byte prefix/suffix. Its remaining **40,130-byte interior** has only 2.4072% zero bytes, **7.9566401 bits/byte entropy** and 37.79% printable bytes. The unrelated 17⊕60 original control has **3,053 total equal bytes** and a **40,077-byte interior** with 1.2002% zero bytes and **7.9854983 bits/byte entropy**. The source pair's somewhat elevated interior equality is an original-image relationship; it does not constitute readable plaintext, a file format or an authenticated XOR message. Four mixed source/control pairs likewise produce high-entropy interiors (7.9689–7.9877 bits/byte).

To decide whether that elevated relationship actually depends on the extracted GP password, the final [passing workflow 43710550136](https://github.com/FlareZ123/liber-primus/actions/runs/43710550136) changes **one ASCII character only** in the candidate password: source exact `DJUBEIAEF` versus wrong-key `DJUBEIAEG`. All four original images still produce the **same wrong-key header**, now `seed=27711, len=40499`. The wrong-key 44⊕72 source-pair interior has **2.4977% zero bytes and 7.9548859 bits/byte entropy**, even *more* pairwise equality than with the putative true source key, while unrelated original controls again produce high-entropy interiors. The pairing signal therefore **fails the key-specificity test**. XOR cannot currently disclose or authenticate a hidden message from either source carrier with this fixed password.

**Stop condition:** No further key permutations, source-page alignments, byte-offset hunts or follow-on decryption should be commissioned from these OutGuess outputs absent a new original author instruction and independent recognizable-byte prediction. The originally intriguing common prefix/suffix and elevated 44/72 matches have a verified one-character wrong-password control. This narrows an actual source-derived hypothesis without asserting that unrelated, untested hidden channels are impossible.

**Decision:** The source-derived password is **not authenticated** by OutGuess output in these two source-selected JPEGs. The key-specific repeated header is equally present in unrelated original page images. Any encrypted, compressed or nonstandard hidden payload would require a separate source-prescribed recognizer and independent positive discriminator; inventing a new XOR or KDF solely from these opaque high-entropy bodies is not warranted. No unknown LP2 key or plaintext follows. Agent1's distinct native OpenPuff test remains an independent question.
