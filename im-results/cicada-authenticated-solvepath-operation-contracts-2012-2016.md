## Source-supported design patterns and limits

**1. Type information usually comes from a concrete source or machine-facing artifact. Confidence: high.** `BASE29` identifies the input integer and output digit alphabet; the signed 2014 upload contract identifies all of `/cgi-bin/upload`, input field `file` and an expected square/service-URL type; the 2014 signed page's literal hex bytes fix a byte/media decoding boundary. In each case a human can know what constitutes an output *before observing whether it spells a desirable phrase*. For LP2, p50 is visibly a table and p56 visibly prints a 128-hex string, but **neither alone fixes the missing table digit alphabet, key operation, hash algorithm or external receiver**. Earlier successes do not permit post hoc choice of the most attractive interpretation.

**2. Operands and clocks may be local to a specific stage, participant, or service. Confidence: high.** The 2013 DH server base/secret are participant-generated; the 2013 NEXT message is client text; the 2014 Stage8 hidden-service URL and hosted CGI are participant-specific. In contrast, signed `BASE29 3301` is a fixed source example and a signed upload endpoint contract is explicit. Thus a numerically attractive cross-year reuse of `23,5,6,15,8,19,2`, `1033/3301`, or `NEXT` is insufficient to transfer hidden state into LP2. **Required new evidence:** a signed or LP2-original instruction assigning the historic operand to an exact original LP2 receiver and clock.

**3. Recognizable success normally produces a new typed object or verifiable next-stage response. Confidence: moderate-to-high.** The 2013 ICMP archive decompresses to a PGP-verified onion address, the 2014 hex page reproduces a particular MP3, the audio reconstruction yields three precisely checkable magic squares, and the Stage10 static response gives byte-exact LP1 images. Here success is independently measurable in **bytes, parseable machine objects, or known destinations**, often with a next-stage source. The limit is that the OpenPuff stage and the 2014 XOR/column route rely on participant inference: Cicada did sometimes expect solvers to discover an operation, and later output matching does not prove that a prior clue specified it uniquely. For unknown LP2, an appealing English four-letter word with no verified inverse or held-out message is much weaker than a complete exact-byte handoff.

**No stable single cipher family** transfers across the signed examples. The operations range from network protocols and numeral conversion to media, web submission and manuscript ciphers. The transferable habits concern **typed inputs, source selection and objective completion checks**. A cultural/numerical allusion can justify a search, but by itself cannot become an author-authenticated key.

## Causal rubric for new LP2 assignments

Before commissioning substantial code, a Director should require an answer to these five questions; record **missing** explicitly rather than silently fitting it.

1. **First-party stimulus:** What visible original rune, image, layout element, signed phrase or contemporaneous source would lead a solver to the operation *before* ciphertext scoring? If source is a reconstruction or a community note, label it.
2. **Type and operand:** What exact original bits/runes/tokens, key bytes, base alphabet, endian convention, length and starting offset are selected by that stimulus? If no source can select among base59/base60 and zero/one origin, the proposal remains exploratory.
3. **Complete action:** Is there an explicit reversible transform or transport protocol, including state transition, F/escape handling, clock, page reset and any dynamic choices? Merely naming DH, a prime, a tree, a compass direction or “next” leaves these fields absent.
4. **Prediction before output:** Freeze at least one **typed** prediction on untouched original LP2 data, preferably a recognizable 30+-rune passage, an exact externally anchored key, a source-signed next object or a valid 128-hex target/link. Require full forward re-encoding for plaintext claims; synthetic positive controls alone are insufficient.
5. **Independent receiver and scope:** Who or what consumes the output, and how is its correctness established without letting the same observed result choose the origin, operation and interpretation? Bound the experiment if only one input family is actually selected; stop rather than spawn parameter rescue branches after a failure.

### Immediate unresolved application

The strongest still-open word-directed route is [2016 source → p50 functional graph → p32](lp2-p50-functional-graph-2016-wordmap.md). It passes **stimulus and reproducible navigation**. It still lacks a first-party instruction choosing a GP0/radix/serialization convention and, above all, **a reversible action consuming p32's 121 original GP29 runes**. The parallel [p56 destination-hash project](lp2-human-solve-path-audit-2026-11-21.md) lacks an authenticated algorithm, source bytes and host; the newly opened Director #2030 rightly demands a first-party link before promoting an attractive domain. These are precise missing inputs. This profile does not authorize a fresh numerical map or broad cipher sweep.

**Decision for #2031:** maintain diverse exploratory work and source recovery, but require an originally visible type/operand/operation/receiver chain for promotion of a decryption claim. As a constraint on false paths, this is supported by concrete earlier handoffs. As a method of *solving* LP2, it is a prioritization rubric only, not an independent cipher key or plaintext.
