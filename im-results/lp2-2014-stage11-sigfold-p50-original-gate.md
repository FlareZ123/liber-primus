# Contemporary 2014 RSA-signature FOLD versus the 256-byte LP2 numeral field

**Agent8, 23 November 2026. Classification:** distinct historical byte-layer source experiment; nine direct original-input negative results. **No unknown LP2 plaintext, key, new authenticated instruction, or destination.**

## Independent candidate route

The authenticated **2014 Stage11 handoff** to the original Liber Primus delivery onion, preserved as `resources/historical/cicada2014-stage11-message.asc`, contains a valid OpenPGP RSA-4096 signature with a source-encoded **512-byte signature MPI**. The original LP2 physical p14 (31.jpg) prints the literal complete word **FOLD** (rune offsets2–5), and the originally printed p49–51 numeric panel contains exactly **256** two-glyph numeral cells, provisionally read as **256 bytes** in conventional base60.

A contemporary 2014 player could possess all three original objects. One direct, falsifiable interpretation is to **fold** the 512-byte RSA signature into two 256-byte halves, use the first half, second half, or their bytewise XOR as an explicit256-byte key, and invert the numeric field as a bytewise ciphertext. The exact table length is an independent size selector; the original source offers no direct instruction that OpenPGP signature *data*, rather than its successful verification, supplies a cipher key. This is a strictly conditional hypothesis.

This source distinguishes the experiment from the earlier [2016 signature half-grid test](signed2016-signature-half-grid-inverse.md), which used a signed message that did **not exist** when the book was originally released, and from the [2014/2016 RSA MPI cyclic GP29 pad test](lp2-signed-openpgp-mpi-directpad-gate.md), whose receiver was the **runic book text**, not the p49–51 byte panel.

## Frozen complete original receiver

Parse the genuine 2014 Stage11 armored signature to the original543-byte RSA signature packet; its terminal512 bytes are the original 4096-bit MPI. Read all256 table cells in original printed order as authentic source-compatible base60 values. Construct three fixed256-byte pads from that single signature: first half, last half, and first-half XOR last-half. For each, attempt the three universal bytewise reversible operations `cipher XOR key`, `cipher − key mod256`, and `cipher + key mod256`. **No secret value, offset, table permutation, word crib or ranked parameter is fitted.**

Every 256-byte original output reencrypts exactly into all original source values. Nine independently planted 256-byte ASCII messages encrypt under the paired operator and recover byte-for-byte. For an immediate recognizable success, a genuine uncompressed natural-language byte payload would exhibit substantially more ASCII printables and longer printable runs than random bytes. The actual outputs were:

| Fixed 2014 signature pad | XOR printable (max contiguous run) | Subtract printable (max run) | Add printable (max run) |
|---|---:|---:|---:|
| First 256 bytes | **92/256 (6)** | **89/256 (5)** | **84/256 (3)** |
| Last 256 bytes | **102/256 (8)** | **86/256 (5)** | **102/256 (4)** |
| XOR of both halves | **99/256 (5)** | **94/256 (6)** | **88/256 (7)** |

No result begins with sustained natural text or a recognizable uncompressed common-file signature. The original upper bound is **102 printable characters out of 256** and the longest run of printable characters is eight. Those byte streams are incompatible with a direct ordinary ASCII key/instruction payload, subject to the possibility of a further compression/cryptographic layer unselected by any original source.

**Reproducer:** [read-only source-original Windows Node22 CJS](../sims/lp2_2014_stage11_sigfold_p50_sft.cjs), [Windows Actions PASS 45097169781](https://github.com/FlareZ123/liber-primus/actions/runs/45097169781). It reads the historical armoured signature, the canonical original p50 grid and literal p14 word from primary-derived source, asserts exact RSA packet/table sizes, and executes the nine inverse/positive checks.

## Decision

Reject **unmodified 2014 Stage11 RSA signature halves or their XOR as a direct bytewise encryption key for the printed 256-byte table** under all three ordinary operations. This does **not** exclude a genuine unseen table cipher, a non-ASCII payload, a different source-specified mixing operation, or the signature's intended authentication role. Without a first-party selector, additional permutations/KDFs and large retrospective signature-pad hunts would be overfitting.
