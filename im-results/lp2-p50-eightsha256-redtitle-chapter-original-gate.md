# P50 32×8 table versus eight original red titles and chapter SHA-256 digests

**17 November 2026 · Agent29. Classification: bounded original-input negative; no recovered LP2 plaintext or key.**

## Source selection and two serious alternatives

The original physical pp49–51 print a **32-row, 8-column** numeric table. Under the repo's conventional, image-adjudicated base60 interpretation, the complete row-major stream is 256 bytes. Each *printed column* independently contains exactly **32 bytes**, the output length of SHA-256. The entire 256-byte table can also be partitioned in printed row-major order into eight contiguous 32-byte blocks. A possible creator-era function would be eight SHA-256 digests of eight source-delimited input strings. SHA-256 was historically available to Cicada creators, but **there is no surviving source instruction declaring any of the eight table columns a SHA digest, nor selecting an input serialization**. The alternative is an ordinary numeric field or encrypted/random payload.

Freeze the eight distinct physical opening red titles p0,p3,p8,p15,p23,p27,p33,p40, and, independently, the eight original red-title-delimited *complete preterminal chapter-body source streams*. Their exact page sets are p0–2, p3–7, p8–14, p15–22, p23–26, p27–32, p33–39, and p40–53 (p50 has zero runes). These original source intervals have **729, 1145, 1729, 1903, 1021, 1433, 1680, 3008** GP29 runes. For each red heading, fix five direct, unkeyed byte serializations: raw GP29 indexes 0–28, GP29 indexes 1–29, assigned prime values, original rune glyph UTF-8, and canonical uppercase romanization. For each full chapter, fix two direct readouts: raw GP29 indexes and original rune glyph UTF-8. No IV, salt, caption cuts, alternate alphabet reordering, null removal, nonce, custom digest, secondary hash, key guessing, or source text changes are permitted.

For each of the **56** predeclared source byte strings (40 title and 16 body), calculate SHA-256 and compare all 32 digest bytes exactly against each of the **16** table candidates (8 physical 32-byte columns plus 8 contiguous printed row-major 32-byte chunks). This is **896 exact whole-digest comparisons**. SHA256(`abc`) must first equal the standard known digest `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`.

## Original result and cryptanalytic fork

An independent pure JavaScript SHA-256 direct computation on the unmodified GitHub source files yielded **zero complete digest matches in 896 comparisons**. The SHA-256 known vector passed. As a spot check, the first red p0 heading serialized to raw GP29 index bytes hashes to `07dc59e39cd4837ac9fa61b65763f8a21dadbd0aaff29f064f720d77ab4dc9db`. A separate standard-library Python test of the **40 original red-heading SHA inputs** against the identical 16 table chunks independently gave zero matches. An additional input-independent historical source comparison found no exact equality of those sixteen table chunks to any of the 75 unchanged original JPEG SHA-256 checksums listed in `resources/liber-primus/SHA256SUMS.txt`; this is a limited additional hash-string observation, not a predeclared author clue.

**Decision:** The table does not literally contain SHA-256 digests of these eight original headings or eight red-title-delimited ciphertext sections under the fixed plain serializations and two natural 32-byte readouts. This narrow no-key route is retired. It says nothing about keyed hash outputs, alternative data or a cipher-bearing 256-byte table; no source clue currently specifies such a new expansion, so do not convert the negative into a KDF/nonce/serialization search. Actual LP2 p0–55 plaintext remains unknown.
