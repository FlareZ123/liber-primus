# May 2014 original LP2 carrier set: complete 58-JPEG exact-byte check

**Consolidated decision, 26 November 2026.** All **58** JPEGs in the project's canonical unsolved Liber Primus release are exact Git-object byte matches to the **58** individual page images in a historical participant's archive committed **11 May 2014**. Its containing directory preserves no extra key-bearing sibling file. The original HTML delivery index has only the static title `133`, div ID `331`, and 58 relative JPEG references, with no code or bytes implementing a decipherment. This rules out a modified modern source image or a missing same-directory file as the cause of failure to decrypt LP2. A full OutGuess 0.4 census of the **58 original LP2 DCT retrieval bitmaps** now finds the same 128-byte all-`ff` prefix on every page (SHA-256 `e9175db65a9789096ca9cb5524d3abc2107df03e3c9ba3af1aca628f9c5d3bd2`): the first 32 encrypted header bits are therefore source-forced to `ffffffff` under every password. With the historical default key, 16/58 extractions complete with the same decoded header `c0a128e3` (seed 41408, length 58,152) but yield high-entropy non-text; 42/58 fail before completion. This rejects default-key output as payload evidence. It does **not** prove that the JPEGs lack embedded payloads: a non-default, independently source-selected key or a different coefficient-domain receiver remains possible. Several frozen native OpenPuff JPEG extraction configurations have also yielded corrupted-stream rejections without key recovery; no unknown LP2 plaintext is known.

**Independent chroma plane (28 November):** Direct libjpeg coefficient reads on all 58 originals find 23 one-component images and 35 color images. At a fixed red/gray quantization-plus-8 residual tolerance, 34/35 color scans have no violating block; all 568 violations occur in the bottom p22 corpse artwork, where the amplified color residual follows the existing drawing and correlates with luminance edges (Spearman .6853). The faint chroma arrays on several otherwise monochrome pages repeat exactly with reused artwork. This disfavors a separate, substantial non-red color signal in the body text; smaller residuals, palette-conforming or arbitrary coefficient-bit encodings are not excluded. [Calibrated chroma decision and exact output](lp2-original-chroma-source-gate.md).

## A verification-record boundary that does **not** transfer to the p56 digest (Director #3304, 28 November)

The original 2014 source has a concrete first-party, recognizable **message versus authentication-record** syntax, but no surviving matching **payload versus digest-record** syntax for LP2. It is important not to confuse the two kinds of hash.

- The original signed Stage10 form (`resources/historical/cicada2014-sixth-onion-v2-form.html.asc`, **1,350 bytes**, Git blob `ff4d21ad4e56836070f431a6a297ab14a10a099b`) and Stage11 handoff (`resources/historical/cicada2014-stage11-message.asc`, **1,183 bytes**, Git blob `e2b7382ac2cfb0adfe028cc063fc6048e0ad718e`) each have the exact ASCII delimiters `-----BEGIN PGP SIGNED MESSAGE-----`, `Hash: SHA1`, `-----BEGIN PGP SIGNATURE-----` and an armor footer. Their `Hash: SHA1` is part of the PGP signature/verification mechanism for **those signed messages**, not an instruction to SHA-1-hash LP2 pages. The supported verification operand is the cleartext inside each signed envelope under OpenPGP canonicalization, not a free-standing image or a hidden external web page. In particular, SHA-1's 20-byte digest is **not** the 64-byte p56 target.
- The original **1,640-byte** Stage11 HTML (`resources/historical/cicada2014-onion7-original-index.html`, blob `303db130705f0ef9be2a738f4336d5cfcebde80c`) is not PGP armor, has no `Hash:` header, checksum, detached signature, digest tag, script, or extra relative resource. Its **58** `img src` values are exactly `0.jpg` through `57.jpg`, one per visible image. The surviving original directory includes no sibling verification record; the historical Stage11 handoff identifies the .onion hostname but not a page-specific hash operand. The separate original-JPEG segment census below already excludes page-specific APP/COM metadata or appended file payloads, without ruling out all DCT steganography.
- LP2 p56 prints an unlabelled, 128-hex-character numerical target on a **rendered page**, and says an external page hashes to it. That is a *criterion to search for an external page*, not the kind of byte-delimited, author-attested PGP verification wrapper above. No preserved original LP2 HTTP response, header, MIME metadata, detached signature, named hash algorithm or canonical target byte slice binds the p56 value to a specific payload in the 58-image distribution.

**Reproducible minimal comparison:** read the three tracked UTF-8 files without newline normalization; regex-match the `BEGIN PGP`, `Hash:`, `BEGIN PGP SIGNATURE`, `img src`, `src|href`, and 128-hex strings. This was executed on exact GitHub blobs. Counts: **2/2** signed forms declare `SHA1` with an explicit signature boundary; **0/1** release indexes contains any verification field; **58/58** image references are consecutive numerical JPEG paths; **0** other `src/href` destinations. Existing source-byte checks already exclude the unchanged index's exact 1,640-byte SHA-512/SHA3/BLAKE2b digests as the p56 value; do not re-hash alternative whitespace variants without a first-party canonicalization rule.

**Decision:** this actual 2014 authentication syntax supplies **no receiver/key/p56 preimage** for LP2. The specifically missing witness is an author-selected digest grammar with *both* an exact independent byte operand and a stated digest/canonicalization rule or a signed instruction binding one to the p56 target. It would be a category error to infer `SHA1` for p56 from the separate PGP envelope. This retires the local verification-record interpretation, not the remote-page continuation or a future authenticated external object. No change to the authoritative plaintext frontier is warranted.

## Original-byte JPEG header-channel decision (Agent 46, 15 November 2026)

A read-only **58/58 original JPEG** census tests the low-cost possibility that a hidden key was delivered as different APP/COM metadata, a modified quantization table, or bytes appended after the JPEG end. The [standalone original-input Node22 test](../sims/lp2_jpeg_header_sft.cjs) traverses source-order files `17.jpg`–`74.jpg` and parses their complete pre-SOS marker headers, baseline component inventory, entropy-stream end marker and tail, with an injected synthetic COM-positive control.

**Exact observed constraints:** every scan has a single APP0 JFIF and a single APP2 ICC segment with **identical full SHA-256 payload digests** across all 58. The ICC string is the same `Artifex Software sRGB ICC Profile`. All 58 use one identical luminance DQT table; 35 three-component RGB files additionally use one identical chrominance DQT table. The other 23 JPEGs are single-component grayscale. Each has exactly one baseline SOF0, one SOS, and no bytes after its EOI. There are **zero APP1/APP3–APP15 or COM segments**, and therefore no image-specific metadata fields of those types. The adaptive Huffman (DHT) segments and compressed pixel data vary with the pages and were **not** interpreted as a hidden message.

**Decision:** no page-specific APP/COM metadata key, modified JPEG quantizer or appended file payload exists in these exact published bytes. This is a *narrow original-input exclusion*, not a negative for pixel/DCT steganography, a key encoded in linework, or an unknown external source. No unknown plaintext follows.

## Lossless JPEG entropy/Huffman origin test (Agent 10, 17 November 2026)

An independent original-image encoding question is whether the 58 released scans hide a separate signal through a freely selected Huffman table or noncanonical compressed entropy representation, above and beyond their quantized DCT coefficients. The new [read-only 58-image libjpeg test](../sims/lp2_jpeg_huffman_reencode_sft.c) extracts each original JPEG's *unchanged quantized DCT coefficient arrays*, recompresses those coefficients with libjpeg `optimize_coding=TRUE` and the image's original critical parameters, then compares both exact DHT segment bytes and the complete post-SOS entropy-coded payload, ending at the original EOI. It neither modifies source coefficients nor compares visually re-encoded pixels.

**Direct-byte result: 58/58 DHT streams and 58/58 entropy streams are byte-for-byte identical to the deterministic optimized coefficient-transcode output.** The comparison is stronger than identical DQT/APP headers and covers the entire variable-length Huffman coding of the published image coefficients. **Historical positive-carrier contrast:** eight independent original LP1 scans with authenticated, recoverable OutGuess data (`00`, `01`, `02`, `03`, `08`, `11`, `12`, `13.jpg`) all have DHT tables and compressed scans that **differ** from this exact optimized coefficient transcode. Seven LP1 scans without authenticated OutGuess payloads (`04`, `06`, `07`, `09`, `14`, `15`, `16.jpg`) all match it exactly. Thus the actual known OutGuess carrier set is separable by this simple byte-for-byte encoding fingerprint on 15 contrasting historical scans, whereas **all 58 LP2 images have the unchanged-cover pattern**. The original LP1 `04.jpg` produces an unauthenticated default-key pseudo-payload despite having the unchanged-cover fingerprint; it is not a positive stego control. The source `10.jpg` contains concatenated image streams and is deliberately left outside this single-stream comparison. This is empirical evidence against the *unmodified historical OutGuess carrier writer* having produced the LP2 files; deliberate post-embedding optimized transcode or other coefficient-domain codecs remain viable.

**OutGuess 0.4: authentic LP1 controls and full LP2 original-header census (Agents 9 and 3, 17–26 November).** The controlled [single-file reproducer](../sims/lp2_outguess_optimized_authentic_control_sft.py) reads the eight historically authenticated LP1 carriers (`00,01,02,03,08,11,12,13.jpg`), losslessly reencodes their quantized DCT coefficients with libjpeg `optimize_coding=TRUE`, and applies the calibrated OutGuess-0.4 decoder to both versions. All eight authentic messages recover byte-for-byte with equal SHA-256; the seven LP1 non-authenticated contrast images also preserve their complete coefficient bitmaps. The original LP2 census now covers **all 58** files `17.jpg`–`74.jpg`: every retrieval bitmap begins with the same 128 bytes of `ff` (SHA-256 `e9175db65a9789096ca9cb5524d3abc2107df03e3c9ba3af1aca628f9c5d3bd2`). OutGuess 0.4 samples its first 32 encrypted header bits only within those first 1,024 bitmap bits, so the retrieved encrypted header is `ffffffff` on every page regardless of password. Under the historical default key, the fixed decoded header is `c0a128e3` (seed `41408`, length `58152`): **16/58** images complete extraction, but all 16 outputs have entropy `7.996411–7.997115` bits/byte and printable fraction `0.380847–0.387313`, with no recognized file signature; **42/58** fail before completion (39 zero-skip-modulus failures, 3 declared-length-exceeds-bitmap failures). The complete outputs are source-forced pseudo-extractions, not authenticated messages. The three earlier representative LP2 samples (`17,57,72`) still preserve their complete bitmaps through optimized-Huffman recoding. The separate p28 `key=79` known-key positive is an embed/retrieve calibration on a temporary modified copy of scan `17.jpg`, not a payload recovered from the unchanged original scan. This establishes that authentic LP1 OutGuess messages survive Huffman optimization while the default-key LP2 extraction is non-evidence; it does not exclude a non-default password independently selected by a clue, deliberate post-embedding coefficient-preserving optimization, or another receiver.

**Decision and boundary:** the original LP2 Huffman/entropy representation contains **no independently varying DHT-codebook or entropy-bitstream payload relative to this fixed, lossless optimized encoder**. The full 58/58 OutGuess 0.4 bitmap census separately rejects default-key extraction as payload evidence; the source-forced header is not a password selector. A non-default password is worth testing only if an independent clue selects it. A malicious payload encoded into the *quantized DCT values themselves* could survive exact recompression and is **not universally excluded**; other coefficient-domain receivers likewise remain possible only with a source-supported operation. No plaintext, private key or external continuation was recovered by these tests.

## Scope and next cryptanalytic decision

The true unresolved source is a **key-bearing original Cicada payload or typed cipher instruction**, if one existed beyond the published image set. Original May2014 Stage11 consists of 58 identical known scans and static HTML; its signed handoff offers no codec or selected page. The private communication/upload mechanism in the preceding Stage9–10 messages could have carried solver-specific data, but the public archived form and static reply do not preserve actual POST bodies or private replies. No key from that private channel is established.

The **original Windows OpenPuff 2014 MP3 positive control passed** on 15 November 2026, recovering the authentic 745-byte magic squares under historical password `33011033` ([source-native report](openpuff-jpeg-capacity-gate.md)). Subsequent native Windows OpenPuff 4.00 attempts on the original 58-image JPEG chain have actually executed and returned **corrupted stream**, including the original publisher order and the independently frozen 133/331 affine carrier order with A=`33011033`, B/C off, JPEG Medium 1/5. The original signed material does not choose an alternate password or image order. [Exact historical carrier test](../workplace/lp2-onion7-html-affine-openpuff-58-source-gate.md). These configurations are excluded; JPEG steganography in general remains open. Future research needs an authored pointer to specific carrier bytes or a genuine cipher operation, rather than repeating alternate settings without a source selector.

**Result class:** exact original-source identity plus a missing-link decision. **No recovered unknown LP2 plaintext, authenticated key or final destination.**
