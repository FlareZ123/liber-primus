# Cuneiform prime ranks → 58-page image indices → LX: exact source chain, missing instruction

**Agent8, 17 November 2026. Status: source-exact structural candidate, not an authenticated instruction or LP2 decryption.** Director [#1392](https://github.com/FlareZ123/liber-primus/issues/1392) asked whether the distinctive 1033/3301 cuneiform and earlier Cicada prime presentation actually select a human-executable 58-page navigation/radix rule. The finite source check confirms the whole proposed numerical/visual route and identifies its unresolved authorial step. **No original unknown plaintext, key, or cipher inverse was recovered.**

## The complete reproducible original-source chain

1. The preserved 2013 CicadaOS [`prime_echo` source](../resources/historical/cicada2013-os-original-prime-echo.sh) emits exactly 464 consecutive primes as literal shell `echo` lines, from 2 through 3301. Only the 1033 and 3301 echo lines have two-second pauses. Counting from one, **1033 is line/prime 174 and 3301 is line/prime 464**. The source pauses on *values*; it does **not** print the ordinal numbers 174 or 464, so counting is a solver operation.
2. The contemporary participant-preserved [2014 Stage11 HTML](../resources/historical/stage11-2014-index.html), [pinned manifest](../resources/historical/stage11-2014-index-manifest.json) has 58 sequential JPEG source names `0.jpg` to `57.jpg`; it has no script, index formula, or numeric navigation instruction. Integer division of the ordinals by the original visible page count gives **174 / 58 = 3** and **464 / 58 = 8**, both exact, as zero-based page indices. This use of quotient rather than remainder is **inferred**.
3. The source's original images `3.jpg` and `8.jpg` are mirrored as combined scans [`20.jpg`](../resources/liber-primus/20.jpg) and [`25.jpg`](../resources/liber-primus/25.jpg). Both start physically marked chapters with a monumental red initial. Source [GP29 corpus](../resources/liber-primus/lp2-corpus.json), page-local rune offset 0, independently reports **p3 rune index20 = L**, **p8 rune index14 = X**. In source page order these letters spell **LX**, Roman 50 + 10 = **60**.
4. The original cuneiform on pp33–39 already encodes its two numbers in **base 60**, and the source p50 32×8 numeric cells have a plausible sexagesimal interpretation. Consequently LX=60 is a coherent **radix hint**, although it currently adds no specified cipher operation, key, input interval, or message receiver.

## Independent challenge to the inferred navigation

**Indexing objection:** the proposed indices **3,8** use `floor(rank/58)` on **one-based** ranks. A conventional zero-based grouping of 58 successive primes uses `floor((rank−1)/58)`, which instead yields **2,7**; conventional wrapping into the actual 58 visible page slots gives `(rank−1) mod58 = 57,57`. Hence the attractive 3,8 result specifically requires placing the 58-prime block *boundary* on the next page or using an unusual 1-based/0-based mix. No original source selects that boundary rule. This is stronger than mere /29 competition and prevents promoting the LX connection as a naturally implied page address.

The same ordinal counts are **174 = 6×29** and **464 = 16×29**. Dividing by the explicitly authored **29 GP runes** selects source pages 6 and 16 instead, both valid visible pages in the 58-page book. The true first runes there are **p6 X** and **p16 E**, and neither image starts a physically marked chapter: p6 begins black running text and contains an internal red paragraph initial; p16 begins black running text. The `/58` route therefore has a real *pre-score, visible structural advantage* relative to `/29`: it selects two large initial pages and reads a meaningful base-60 number. This comparison does not make `/58` author-selected, because the choice of testing prime-rank quotient and Roman numeral was made after seeing the same artifacts.

One additional dependence prevents counting three independent confirmations: [Stage11 HTML](../resources/historical/stage11-2014-index.html) has `<title>133</title>` and `<div id="331">`, so 133 + 331 = **464**, the same prime rank of 3301. But this earlier artifact also relates to the preserved 2014 7×7 sum-1033 magic square with center 331; the HTML already displays the images in ordinary page order. The 464 coincidence cannot separately authorize page-index division, as documented in the [2014 Stage11 source audit](2014-stage11-133-331-prime464-original-gate.md).

## Decisive missing evidence / decision

- No Cicada-authored or contemporaneously preserved instruction in the inspected prime-echo program, [signed Stage11 handoff](../resources/historical/cicada2014-stage11-message.asc), or original HTML says **count the pauses' ordinal positions; divide by number of book pages; read initial runes as Roman numerals**. The cuneiform numerals themselves need base60 for their established reading, making LX a possible retrospective confirmation rather than an independent radix selector.
- Crucially, even granting all navigation steps as true, the endpoint is only the number **60**. The existing sexagesimal representation of cuneiform and p50 cells does **not** specify how to read, key, transform, or invert any of the 12,956 encrypted runes. There is no complete decoder to freeze or withheld plaintext to predict. Trying arbitrary base60-to-GP mappings now would violate the issue's source-selection gate.
- A meaningful next step would require *new, independently dated first-party evidence* selecting the ordinal/page-index method **and** a concrete receiver for the resulting 60 (for example a named p50 table reading/byte serialization with fixed frame and key). Without it, retire the cuneiform→LX hypothesis as a speculative **structural observation**, while retaining the exact source arithmetic.

It does not disprove other source-authored uses of the 1033/3301 pair, other base60 transports, or other algorithms.
