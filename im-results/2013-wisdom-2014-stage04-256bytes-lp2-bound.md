## Independent 256-byte bridge, bounded and controlled

The historical site's 256 original bytes form a fixed complete byte string, just as the manuscript's original printed 32×8 base60 table contains 256 separate byte-representable pairs. The 2014 puzzle genuinely used bitwise XOR and byte reversal elsewhere, making a direct parallel-byte XOR a finite, human-plausible **testable analogy**. There is still no direct instruction saying the two objects should be combined.

Take all source site-hex bytes as printed and all current original-JPEG-adjudicated table bytes in row-major order. Test only exact source order or reversal of the table (both operations occurred in 2014 stages). Compare a full `256`-byte XOR output for printable US-ASCII and first bytes; a valid plain ASCII output of this direct type would require every byte printable. This is an intentionally narrow test, not a search for arbitrary stego/key algorithms.

| Frozen source pairing | Exact site/table byte matches | Printable ASCII after XOR | First sixteen decoded bytes (hex) |
| --- | ---: | ---: | --- |
| Direct source order | 1/256 | **99/256** | `4c39fcc5c387c6ea7eaf588d10f10bee` |
| Reversed table order | n/a | **101/256** | `d7637fcb44c6262ce290fc4531df31aa` |

Neither output is literal ASCII text or a recognized first-byte plaintext signature. A 256-byte synthetic ASCII message combined with the same original table under XOR is recovered exactly, **256/256 printable**, so the implementation positively detects the declared simple mode.

[Reproducer](../sims/stage04_1033_html_lp2_256_gate_sft.cjs) reads the two committed source bytes locally, checks the site marker, 512-digit hex, 32×8 table geometry, and exact direct XOR output. The test was independently calculated using the exact same original byte arrays before the SFT was committed. A permutation, unknown key, later cipher layer or non-ASCII binary is outside the stated negative. The original manuscript has **no stated rule** connecting the historical site data to its 32×8 table: equality at 256 bytes is not a cryptographic relationship by itself.

The immediately preceding **2014 stage03 second-onion** preserved page is also a fixed 256-byte hex string, under a different explicit comment **`<!--Patience is a virtue-->`**; it is preserved verbatim in [`resources/external/2014-stage03-index.html`](../resources/external/2014-stage03-index.html), linked to the original [second-onion archive](https://github.com/krisyotam/cicada3301/tree/main/puzzles/2014/assets/stage03/cu343l33nqaekrnw.onion). Its full 256-byte sequence differs from stage04 at **254 of 256 positions**. The [2014 chronological walkthrough](https://github.com/scream314/cicada3301/blob/master/2014.md) reports that both onion sites transmitted growing hexadecimal streams over time, with two characters per new byte. Their 256-byte framing therefore has a documented **historical staged-release purpose**, weakening the uniqueness of the proposed LP2-table 256-byte match.

The same source-order three-way XOR (second-onion bytes ⊕ third-onion bytes ⊕ LP2 printed table) yields **91/256 ASCII-printable bytes**, first sixteen hex bytes `2f7b6e7f8a79f584a4752f1724f441dd`. Across all eight direct/reverse choices for the three complete input streams and whole-output bitwise complement, the best result is only **102/256 ASCII-printable bytes**, never a legible plaintext or source-selected file format. The exact source input bytes and complete alternatives were tested from the two archived HTML pages and unchanged canonical LP2 byte table. No arbitrary index offset, key schedule or word segmentation was fitted.

## Numbered-stream to LP2 cuneiform bridge and RSA geometry (Director #1206, 16 November 2026)

**Actual original cue.** LP2 physical pages 33–39 repeatedly show the two cuneiform numerals `(17,13)₆₀ = 1033` and `(55,1)₆₀ = 3301`. This is a stronger source association than the 256-cell table's mere length match, but it specifies neither a receiver nor an encoding operation. In the 2014 contemporaneous chain, the third onion displays `<!--1033-->` followed by 512 hex digits (256 bytes), and the following fourth onion displays a **different** `<!--3301-->` followed by 512 hex digits. The preceding second onion has a **third** 256-byte value, originally under `<!--Patience is a virtue-->`, later rendered as `<!--761-->`. The 2014 participant witness [scream314 2014.md](https://github.com/scream314/cicada3301/blob/22d81c320256dc0d6da030a17b26b6cacfadcea6/2014.md#L164-L185) and [third/fourth onion records](https://github.com/scream314/cicada3301/blob/22d81c320256dc0d6da030a17b26b6cacfadcea6/2014.md#L288-L416) preserve exact strings and chronological presentation. The original numbered two-stream hypothesis must distinguish the 1033 and 3301 HTML operands from the earlier 761 stream and from 2014's known magic-square numbers.

**Historical operator is scoped to other bytes.** The 2014 source-documented XOR ([stage03 source notes](https://github.com/micheloosterhof/cicada-2014/blob/master/stage03/README.md)) combined **three PGP-extracted image payloads** before a 14-column transposition. It gives no command to XOR the two numbered **site hex objects** or read them as GP29. The signed Stage10 instruction's actual receiver was the three magic-square textareas plus a Tor URL/CGI upload ([original signed instruction preserved in 2014 walkthrough](https://github.com/scream314/cicada3301/blob/22d81c320256dc0d6da030a17b26b6cacfadcea6/2014.md#L626-L673)). Independently, `33011033` served as a historically successful OpenPuff A-password for the MP3, yielding `magicsquares.txt`. Thus the repeated numbers have demonstrated earlier-stage uses, and a separate hypothetical byte-stream-to-LP2 key is not established.

**New, finite RSA consumer check.** The same authentic 2014 1033.jpg message announces RSA-OAEP `e=65537`, `n=7557912574608535164426718292058021255641310207187633095795069445700059210248050757270234679993673844203148013173091173786572116639` ([source](https://github.com/scream314/cicada3301/blob/22d81c320256dc0d6da030a17b26b6cacfadcea6/2014.md#L114-L140)). Its modulus is **432 bits**, so a canonical RSA ciphertext block is **54 bytes**. A raw 256-byte stream cannot be divided evenly into such blocks (`256 = 4×54 + 40`). The tempting alternative `4 × 64` bytes, incorrectly treating the original modulus as 512-bit, is invalid: all four big-endian 64-byte chunks exceed `n` in **each** of the exact 761, 1033 and 3301 original strings. Chunk bit-length vectors are respectively `[511,512,511,510]`, `[512,512,512,512]`, `[512,511,510,512]`; valid raw RSA ciphertext integers must be below the modulus. This excludes *direct concatenated historical RSA-OAEP blocks* under the already published RSA key, without inventing padding, offsets, custom framing, or a new modulus. It does **not** exclude some independently instructed byte permutation or a different key family.

**Decision / stopping rule.** The numbered streams are real 2014 original-site operands and the cuneiform numerals are real manuscript signs. The checked 2014 signed instruction names magic squares as the receiver, while the known XOR and RSA routes have separate, incompatible original inputs/packaging. No located first-party source selects `{1033 stream,3301 stream} → GP29 alphabet, combine operator, start state, word/page clock, p33 receiver`. **Do not** enumerate XOR/add/rotate/byte-mod29 and select a high-scoring p33 plaintext retrospectively. A future first-party instruction specifying that missing receiver would reopen the bridge; absent one, the original source gate fails and none of the 1,680 original p33–39 runes is claimed deciphered.

## Next decision

The within-artifact 2014 GP-prime-sum map is established. The contemporaneous 2014 `<!--1033-->` marker explains why 1033 was relevant in that stage. The two 2014 sites' independently framed 256-byte data are preserved as genuine historical artifacts, but direct XOR coupling of either or both with LP2's 256-byte numeral table has no recognized plaintext. Directly transferring the matrix bearing graph, selected 2014 square-cell labels, simple bytewise XOR or arbitrary 5×5→32×8 reshapes would retread already rejected, unselected routes. Unless a new source supplies that operation, the historical square should remain an explained earlier-stage artifact.
