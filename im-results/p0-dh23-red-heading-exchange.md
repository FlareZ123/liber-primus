# p0 red-heading BASE29 / historical DH23 exchange candidate

**Status: intermediate hypothesis; no LP2 plaintext recovered.** This is a source-constrained key derivation worth retaining, not an established cipher solution.

## Proposed human-visible route

The original p0 JPEG (\`resources/liber-primus/17.jpg\`) visibly presents a 13-rune red heading, a 13-dot separator, and a first black line of seven runes. The page also has two marginal stave-like marks, although these have a competing branch-rune interpretation and are not treated as independent DH evidence.

The authenticated 2013 TCP-server challenge (\`resources/external/2013-tcp-server-signed-source.md\`) documents BASE29 conversion and a Diffie–Hellman protocol with prime \`p=23\`, server base \`g=5\`, server-selected exponent, and client-supplied public share. That makes the following reading plausible without inventing a group:

1. Read the 13 red GP digits left-to-right as one big-endian BASE29 integer:
   \`N = 5412445423142629857\`.
2. Use the source-defined group order \`p−1=22\` to reduce the server exponent:
   \`a = N mod 22 = 7\`.
3. The final BASE29 digit of the heading is \`5\`, matching the historical server base.
4. Read the first seven black GP digits after the 13-dot separator as another big-endian BASE29 integer:
   \`M = 1420123033\`.
5. Reduce that value modulo the historical prime to obtain a candidate client public share:
   \`B = M mod 23 = 16\`.
6. The resulting exchange is:
   - server public value: \`A = 5^7 mod 23 = 17\`
   - client public value: \`B = 16\`
   - shared secret: \`K = 16^7 mod 23 = 18\`

The exponent 7 also equals the length of the first black line. The client public value has discrete logarithm 8 in the base-5 group, so the two exchange exponents are 7 and 8. The heading additionally satisfies \`N mod 23 = 0\`, although that is not required by the DH computation.

## Controls and limits

- The canonical p0 rune sequence and red-span annotation support the exact inputs above. The original JPEG supports the 13-rune heading, separator, and seven-rune first line.
- Three of the 18 annotated red spans have BASE29 values divisible by 23 (p0, p15, p33). Applying the same last-digit-as-base reading to the other two gives negative controls:
  - p15's first red span ends in GP digit 24, hence base \`24 mod 23 = 1\`, a degenerate DH base of multiplicative order 1.
  - p33's first red span ends in digit 6 and gives exponent 21. Its first black line has eight runes and BASE29 residue 10 modulo 23. Base 6 has order 11, and 10 is not in the subgroup generated by 6, so that line cannot be a valid public share in the same DH group.
  - p0 is the only one of these three with a primitive base (5, order 22) and a valid client share (16). This is a more discriminating control than divisibility by 23 alone.
- A page-local scan of every 13-rune window on LP2 pages 0–55 finds only the p0 heading satisfying the fixed conjunction \`N mod 23 = 0\`, \`N mod 22 = 7\`, and final digit 5. This is a finite control, not a statistical proof; the scan covers many overlapping windows.
- The first black line's residue 16 is a valid nonzero DH public share, but almost any nonzero residue would be valid when the base is primitive. Its value alone is not a strong discriminator.
- The historical source establishes the protocol and parameters, not that LP2 reuses it or that this exact mapping of red heading and black line to server exponent/client share was intended.
- The two marginal staves may instead be branch-rune material. Do not count them as confirmed DH-party symbols.
- Direct GP29 Caesar use of shared secret 18 and the simple affine test using the derived pair do not produce readable p0 text.
- A frozen attempt to continue the existing 27×27 opening model also fails: treating \`(18,7)\` as row18/column7 selects node \`Y-X-D\`; the same center-totient rule gives \`Y-G-D\`; reusing the opening's +13 center-to-block displacement predicts block start 478. The seven ciphertext runes \`N-P-A-Y-P-C-Y\` decrypt to \`EO-W-U-F-W-J-F\`, not plaintext. No alternate starts, axes, phases, or signs were searched afterward.

## Conditional 2016 word-map cross-check

If the DH outputs are read as page 18, word 7, the canonical printed-word parser used by \`sims/lp2_2016_message_base58_word_map.cjs\` selects \`GAHEALGO\`. It has seven GP runes with prime weights \`[17,97,23,109,73,17,7]\`, summing to \`343 = 7^3\`. It is the only seven-rune word with prime sum 343 among the 2,973 printed words; five words of all lengths have that sum. Its first and last prime weights (17 and 7) match the candidate DH public value and exponent.

This is an interesting conditional consistency, not a plaintext recovery: neither source explicitly says to interpret the DH pair as a page/word coordinate. Applying the provisional 2016 base-58 word-pointer rule to 343 gives p53:w6 (\`DOEER\`), then p18:w5 (\`IDJ\`); the deterministic walk enters a 33-cycle and does not reach solved p56/p57.

## Reproduction and next decision

Run \`node sims/p0_dh23_red_heading_candidate.cjs\` from the repository root. It reconstructs the BASE29 values, DH exchange, red-span and subgroup controls, conditional word-map observation, and rejected 27×27 continuation from the canonical resources.

**Research decision:** retain this as a candidate source-derived key, but do not promote it to \`results/\`. The missing piece is a source-selected reversible LP2 operation that consumes shared secret 18, or an independent second DH-encoded passage that validates the mapping. Do not expand into arbitrary PRNGs, coordinate orderings, or cipher families without another original clue.
