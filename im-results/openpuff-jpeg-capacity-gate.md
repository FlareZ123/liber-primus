**Current state, 14 November 2026 at 21:09 UTC:** An original, source-pinned Windows **OpenPuff v4.00** positive-control run now proves that the program accepts the historical MP3 carrier and reaches its genuine **50% MP3 bit-selection state**. For the better-attested password `33011033`, the original GUI measured **1,088 bytes** of selected capacity, displayed in its locale as `1.088 bytes`. This is a bounded, actionable original-tool experiment. Do not turn capacity or GUI progression into a hidden-payload claim. The next native operation is an **owner-authorized GitHub Actions manual positive-control run** on the now-repaired driver, and only an exact **745-byte extracted file with OpenPuff-native CRC32 `6A8C41E3`** unlocks the conditional LP2-image stage.

The preserved 2014 *Interconnectedness* MP3 has **6,651,873 original bytes**, Git blob SHA-1 `09fe068192b76a3697c47ec1d604b527703db798`, MD5 `7638414d35f416084b7ddcc94aa53685`, SHA-256 `1ce3839b4a62462d9009c4469acc189b523e1bdcf338cb49cda1cd7bb4efffc6`. The [pinned manual workflow](../.github/workflows/openpuff-v400-ui-probe.yml) retrieves these exact source objects and rejects mismatches before launching any cipher operation.

Two historical accounts disagree on the password string. The [neuroretransmit 2014 fifth-onion walkthrough](https://github.com/neuroretransmit/cicada/blob/main/2014/007-fifth-onion/README.md) supplies `33011033` from the literal magic-square column sums **3301** and **1033**, with optional passwords B/C disabled and **MP3 Maximum 1/2**. A [separate iBotPeaches account](https://github.com/iBotPeaches/cicada_3301/blob/master/other/Interconnected_OpenPuff.md) reports `33011103`, the same 50% MP3 setting and recovered 745-byte `magicsquares.txt` with CRC32 `6A8C41E3`. [Connor Tumbleson's first-person December 2024 native replay](https://connortumbleson.com/2024/12/23/the-cicada-3301-mystery-puzzle-3-solve-part-4/) independently identifies **OpenPuff v4.0.0, `33011033`, 50% MP3 bits, name `magicsquares.txt`, size 745 and original CRC32 `6A8C41E3`**, and links a program screenshot. Thus prioritize `33011033`; a published replay, however strong, does **not** replace a current native check against our exact pinned original bytes. The workflow already covers both spellings; no other password guesses are justified.

The source-preserved 745-byte `resources/cicada2014-openpuff-magic-squares.txt` has ordinary zlib/ZIP CRC32 **`5E547914`**. OpenPuff uses an uncommon MSB-first CRC initialized to `0xFFFFFFFF` with polynomial `0x02608EDB`, without final XOR, and for the same exact bytes returns **`6A8C41E3`**. The [original OpenPuff checksum implementation](https://github.com/tweqx/LibrePuff/blob/master/librepuff/src/crc32.rs) and [driver](../sims/openpuff_v400_extract.py) use the native value to authenticate an extracted output. Both size and native CRC are required. The earlier wrong-zlib CRC comparison has been corrected and locally exercised with the actual 745-byte reference.

## LP2 original JPEG feasibility, conditional only

The original release set comprises **58** scans, `17.jpg` through `74.jpg`, all 2,400×3,600 pixels: **35 RGB and 23 grayscale baseline DCT/Huffman JPEGs**. OpenPuff 4.00's [2012 manual](https://www.yumpu.com/en/document/view/37257849/openpuff-steganography-watermarking-embeddedswnet) supports JPEG baseline DCT and offers JPEG **Medium 1/5** as its default; the historical *MP3* Maximum 1/2 setting is **not** transferable to JPEG.

The [independent original-image coefficient census](openpuff-jpeg-capacity-gate.csv), computed by [`sims/openpuff_jpeg_capacity_gate.c`](../sims/openpuff_jpeg_capacity_gate.c), measured **228,411 / 546,300.5 / 788,427** nonzero luma AC coefficients (minimum, median, maximum). Under a separately documented **conditional LibrePuff** arithmetic model, these produce JPEG-Medium candidate capacities **2,560 / 6,224 / 9,008 bytes**. The model assumes one usable whitened bit per nonzero luma AC coefficient and does not implement OpenPuff's JPEG decoder; therefore **none is a verified native capacity, payload or absence-of-payload result**. All 58 exceed the 771-byte historical-size reference under that *conditional* model.

If and only if the exact historical MP3 positive control succeeds, the existing `lp2-jpegs` workflow mode can test **each original JPEG separately** at Medium 1/5, prioritizing original scans **50–56** (physical LP2 pp33–39, containing the creator-visible 3301/1033 numeric motif) then the remaining 51. Each page records `output-file`, `completed-without-file` or `inconclusive-timeout`; a GUI timeout or insufficient estimated capacity never proves no stego. The current 58-page native JPEG stage has **never been run**.
