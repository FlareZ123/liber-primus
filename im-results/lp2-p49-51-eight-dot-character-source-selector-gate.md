# LP2 p49–51: eight-dot character-code selector fails on original ink

**Issue #3318, 28 November 2026.** The 256 source tokens make an eight-bit character-code hypothesis tempting; that hypothesis is **not selected by the physical artifact**. No source-typed full-table Braille/plaintext receiver follows, so there is no warrant to tune codebooks, bit order, radix or glyph readings against English.

## Independent original observations

Original 2014 JPEGs [p49 / 66.jpg](../resources/liber-primus/66.jpg), [p50 / 67.jpg](../resources/liber-primus/67.jpg), [p51 / 68.jpg](../resources/liber-primus/68.jpg) have a continuous **32×8** array of **two-character Latin/alphanumeric tokens**, displayed in **10+13+9 rows**. The 256-cell, 161-unique-token literal transcription is original-image adjudicated in [`lp2-grid-256.json`](../resources/liber-primus/lp2-grid-256.json). The data are not printed as dot-cell glyphs. A 60-digit alphabet and an alternative 59-digit alphabet each yield an admissible but **different** value for every source token; their 256-byte codebooks intersect on all printed strings, so the artifact does not choose radix. The [prior full-table radix gate](lp2-p50-radix-codebook-overlap-source-gate.md) already establishes this observational ambiguity.

The *actual* nearby visual dots deserve direct attention rather than assuming the 8-column count is a code clue. Every p49, p50, p51 image carries **two separated clusters of five geometric sites** within the mirrored tree flourish. The left cluster has three dark/filled circles and two faint/unfilled outlined circles, arranged around a branch as a loose pentagon; the right cluster has five dark circles similarly arranged. The same two tree-and-dot clusters flank **p40 / original 57.jpg** and **p53 / original 70.jpg**, where no 32×8 number field is present. The p49/50/51 dot pattern is visually identical, not a varying symbol at each table cell. Counting eight black circles after combining both sides is a possible *post hoc* coincidence, not an authored **2×4 eight-dot code cell** or a decode order.

## Exact historical character-code type

The [Unicode Braille Patterns specification](https://unicode.org/versions/Unicode18.0.0/core-spec/chapter-21/) describes **256 eight-dot configurations**, represented in a **two-column × four-row** layout and encoded as U+2800–U+28FF. These code points describe **dot patterns**; Unicode expressly does **not** assign their context-dependent linguistic meanings. A contemporary pre-2014 example of a distinct eight-dot ASCII-tied *computer Braille* code is the [UKAAF Braille Computer Notation specification](https://www.ukaaf.org/wp-content/uploads/2020/03/Braille-Computer-Notation-PDF.pdf), which itself acknowledges multiple eight-dot code systems. Consequently even if one independently assumed each p50 token is a byte, interpreting byte `x` as Braille pattern `U+2800+x` is a mechanically defined *visualization*, not a decipherment into ordinary English or an authenticated byte-to-character operation.

Original LP2 gives none of the three necessary selectors: **(1)** a printed 2×4 dot matrix or explicit Braille legend; **(2)** a sender rule selecting conventional radix60 rather than the equally valid alternative radix59; **(3)** a period-authored selection of one eight-dot semantic code/bit numbering and a recipient. Testing both radices, orientation changes, alternative Braille code assignments and printable fragments after seeing decoded strings would be exactly the unsourced scoring forbidden by #3318.

## Decision and future test

**Negative at the independent selector gate.** There is no original eight-dot Braille cell in the examined p40/p49/p50/p51/p53 tree/dot motifs and no source-selected 8-dot character-code convention for all 256 alphanumeric cells. This is **not** a universal proof the grid has no byte meaning, nor that a hidden eight-dot code could not be devised. If an independently dated original author object actually says “read this 256-cell table as [named eight-dot notation]” and supplies a codec/radix/receiver, apply its **entire exact byte stream in row-major order once**, with the external worked example as a positive control and no remapping. Until then do not invoke an invented mapping or treat repeated tree ornaments as a character-code alphabet.

**Outcome:** no new GP29 plaintext, key or continuation; prevents one source-unselected 8-bit codebook search without discarding the numeric panel.
