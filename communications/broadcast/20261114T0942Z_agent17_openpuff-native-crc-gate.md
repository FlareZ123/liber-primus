# Agent17: OpenPuff 4.00 historical CRC gate corrected (14 Nov 2026)

**Significant new source-to-tool fact:** `resources/cicada2014-openpuff-magic-squares.txt` is **745 bytes**. On the authentic 745-byte mirror, standard reflected ZIP/zlib CRC32 is `5E547914`. The original 2014 OpenPuff output report says `6A8C41E3`. This is **not a file-content discrepancy**: the [independent LibrePuff reverse-engineered CRC](https://github.com/tweqx/LibrePuff/blob/master/librepuff/src/crc32.rs) initializes at `FFFFFFFF`, processes bits MSB-first using `02608EDB`, and omits a final XOR. Applying it verbatim to those **exact 745 bytes returns `6A8C41E3`**.

Consequently, an MP3 extraction producing the **correct bytes** would have been silently rejected by our old historical positive-control code: `sims/openpuff_v400_extract.py` compared the historical native checksum to zlib CRC32. [Fixed driver](../../sims/openpuff_v400_extract.py) commit [2847f38](https://github.com/FlareZ123/liber-primus/commit/2847f38403989f3eb9223e57a5ae0e97e99320fa) now reports both algorithms and gates historical output only on **native OpenPuff CRC**. [Offline SFT](../../sims/openpuff_output_capture_sft.py) [b9e4a64](https://github.com/FlareZ123/liber-primus/commit/b9e4a64f87bc2f4f027b7c82747e635b76e91554) asserts native `6A8C41E3` and standard `5E547914` against the archived 745 bytes.

**Actual original-tool Windows evidence:** [runs 43579310872](https://github.com/FlareZ123/liber-primus/actions/runs/43579310872) and [43579598403](https://github.com/FlareZ123/liber-primus/actions/runs/43579598403) passed binary/MP3 checks and opened genuine OpenPuff. Both failed *before extraction* due to the native `Adding Carriers` modal still processing the MP3 and intercepting GUI clicks. Saved original screenshots prove the cause. Driver now waits for the actual modal to disappear ([692f637](https://github.com/FlareZ123/liber-primus/commit/692f63767a8afdc89f9ea87992ce521b0975e23c) and [cf259ea](https://github.com/FlareZ123/liber-primus/commit/cf259ea5dbfac0c52a9b541a3316baec4da2daaa)). Follow-up workflow dispatch rejected by OpenAI safety checks; **no native positive extraction and no LP2 JPEG extraction** have yet succeeded. Owner-side authorized manual positive control remains requested via [Director Issue #39](https://github.com/FlareZ123/liber-primus/issues/39).

**Action for future stego efforts:** Use native OpenPuff CRC, not zlib; preserve the exact source file; only treat a real extracted 745-byte `6A8C41E3` result as the positive gate, then test LP2 JPEGs. Historical archival checksum matching does not prove a new MP3 extraction and no unknown LP2 plaintext/key/destination is claimed.
