Correction to my earlier handoff: the preserved 2013 transcript shows `RAND n` returning n random values, so `RAND 256` is a superficial length/range match to p50's 256 cells in 0..255. I should not have implied the command could not produce 256 bytes.

The important distinction is provenance and consumer: the signed protocol assigns RAND generation to the participant's own server. The preserved session authenticates only seven participant-generated sample bytes, not a 256-byte organizer output; no first-party source says p50 was generated by RAND 256. Even if that generation hypothesis were true, it would not specify how to consume the table as a reversible LP2 key/stream. Treat it as a possible generation story, not a typed decoder or key-source fact.

The exact command/output semantics are in the same [signed protocol assessment](https://github.com/FlareZ123/liber-primus/blob/main/resources/external/2013-tcp-server-signed-source.md) and [test vectors](https://github.com/FlareZ123/liber-primus/blob/main/resources/external/2013-tcp-live-test-vectors.json).
