### Participant-specific RSA page: recovered mirror and reproducible response

**Primary provenance chain.** The archived `unknown.asc` message corresponds to a participant-specific one-time RSA email/page copy. A contemporaneous [AllMystery thread](https://www.allmystery.de/themen/it83189) on **15 January 2012** discusses the unique email and a participant's 112-digit key; another post links the matching Pastebin, and the participant explains that an earlier post was removed to redact the key. The archive's pinned `sources.txt` records the [Wayback capture of Pastebin `HakCdFW1`](https://web.archive.org/web/20120116170758/https://pastebin.com/HakCdFW1), timestamp **2012-01-16T17:07:58Z**. The recovered `unknown.asc` file (Git blob SHA-1 `0e69b063b379a8ccdd8a96815de318bcf65a1247`) contains the one-time warning, 112-digit modulus, encrypted payload and signature packet naming key ID `7A35090F`. The matching extracted payload `unknown.pem` has Git blob SHA-1 `087ed31790eb8931d0255efd34e137ad13163b35`.

This is a **provenance-qualified mirror of the participant's message**, not a byte-preserving capture of the original onion HTTP response. The archive README says only the `quaetrix0` example has a valid PGP signature; the `unknown` and `another_unknown` copies are redacted and their signatures do not verify. Do not describe this copy as cryptographically authenticated. Separately, the valid 2012 `quaetrix0` sample and the 2016 signed message both verify under the same Cicada primary key; both source texts explicitly use short key ID `7A35090F` for signature authentication, not as an address. The 2016 issuer-ID/address-role gate is documented in [the OpenPGP address-role report](../im-results/lp2-openpgp-issuer-id-address-gate.md). The original emailed `/NUM` token is not present in the message or the Pastebin capture.

**Reproducible interpretation.** The `unknown.pem` payload decompresses to a serialized 188-byte `Cyphertext` field: four 47-byte RSA blocks. Using the archived `unknown.private` and `unknown.factors` values (`p*q=n`), the exact `Crypt::RSA` 1.99 implementation recovers four 5-byte blocks and concatenates them to **`29201928111913239376`**. This is the number to enter at the same participant-specific URL according to the message text; it is **not** the emailed `/NUM` path token.

The compatibility detail matters: `Crypt::RSA::ES::OAEP` uses an encoded-message length of `k-1`, while its `DataFormat::mgf1` increments the 4-byte counter by SHA-1's digest length (**20**) rather than by one. Reproducing the source implementation's counters (0, 20 for a 26-byte mask) succeeds; standards-compliant MGF1 does not. The exact source is pinned at [gitpan/Crypt-RSA commit 257f59d](https://github.com/gitpan/Crypt-RSA/tree/257f59d25d2d4adec3ef7e439e89b07a3a21a4ec), especially [OAEP.pm](https://github.com/gitpan/Crypt-RSA/blob/257f59d25d2d4adec3ef7e439e89b07a3a21a4ec/lib/Crypt/RSA/ES/OAEP.pm) and [DataFormat.pm](https://github.com/gitpan/Crypt-RSA/blob/257f59d25d2d4adec3ef7e439e89b07a3a21a4ec/lib/Crypt/RSA/DataFormat.pm).

**Independent cross-check.** The separate `another_unknown.pem` message decrypts under its own modulus/factors to **`25121996842107342310`**. This matches the subsequent onion path `/25121996842107342310` and the account of the later MIDI email in the 11 June 2021 [participant-style retelling](https://saumitrasapre.medium.com/the-mysterious-puzzle-2-c73d805e1f04). Treat that article as secondary corroboration, not a contemporaneous or signature-verified capture. Its archive payload Git blob SHA-1 is `49e290f2e80502c525f931b35c01232b7ee9bcf4`.

**Finite missing-artifact conclusion.** The recovered copy and RSA response are real progress, but the original `/NUM` token and original onion response bytes remain absent. The exact missing record is the initial email from the puzzle sender containing the unique path number, or a server/request log that maps that number to the one-time response. No public source found in this task provides it. Do not brute-force or guess the path token. This historical page recovery and the MIDI stage do not establish an LP2 cipher, key, plaintext, or p56 preimage. See [full reproduction report](../im-results/2012-rsa-participant-page-recovery.md) and [standard-library reproducer](../sims/2012_rsa_oaep_reproducer.py).


### 2012 MIDI chorus and wordlist: documented original decode, not a 7×7 traversal

**Established historical solve, independently reproduced 11 November 2026.** The original [2012 MIDI-stage archive README](https://github.com/neuroretransmit/cicada/blob/main/2012/009-midi-puzzle/README.md) and its [`decode.py`](https://github.com/neuroretransmit/cicada/blob/main/2012/009-midi-puzzle/decode.py) already explain the exact operation. The decoded first musical track instructs participants to create a GPG key, encrypt and sign the **49-word** supplied wordlist with Cicada's key, then submit it to the address that sent the participant's numbers. The second track decodes to the signed Blake stanza repeated **three times**, which supplies the announced chorus/crib. The 49 words are an actual encrypted-submission payload; their 7×7 count does not by itself prescribe grid positioning, start cell, eight-direction map, or next-page address.

A fresh binary parser against archived [`song.mid`](https://github.com/neuroretransmit/cicada/blob/main/2012/009-midi-puzzle/song.mid) (Git blob `11924e0e195208c2eea757655035e149fb8a190f`, 10,889 bytes) reproduced **558** track-1 note-off events and **714** track-2 note-off events. With MIDI event **delta** times (not absolute start timestamps or note durations), the distinct `note + note_off_delta` sums number **25** and **23** respectively. Sorting these sums and mapping to the historically published alphabets `abcdefghiklmnopqrstuvwxyz` and `abcdefghijklmnoprstuvwy` recovers the same full messages printed in the archive README, including the first track's 49 words and the second track's three complete stanza repetitions. Source details: format 1, 96 ticks/quarter, three tracks (metadata plus two note tracks); note pitches are exactly 55/56/58/60/61/63/65/67 and their octave-lower counterparts 43/44/46/48/49/51/53/55.

**Decision:** The MIDI clue is historically accounted for by an explicit two-track substitution decoder and the documented encryption/signing step. Retire the formerly proposed 7×7 word-map / eight-pitch compass traversal as an unsupported LP2 follow-on (Director Issue #93); it would require a separate independently recovered instruction after the solved stage. Do not confuse this rejection of the *route inference* with proof that the 49-word list could have no other hidden use. One participant-specific RSA message copy and its response number are now recovered as documented above; the original onion `/NUM` token and HTTP response bytes remain missing. None of this identifies LP2's encryption key, recovers its unknown plaintext, or gives the p56 hash preimage.
