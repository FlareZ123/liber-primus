### Participant-specific RSA page: recovered mirror and reproducible response

**Primary provenance chain.** The archived `unknown.asc` message corresponds to a participant-specific one-time RSA email/page copy. A contemporaneous [AllMystery thread](https://www.allmystery.de/themen/it83189) on **15 January 2012** discusses the unique email and a participant's 112-digit key; another post links the matching Pastebin, and the participant explains that an earlier post was removed to redact the key. The archive's pinned `sources.txt` records the [Wayback capture of Pastebin `HakCdFW1`](https://web.archive.org/web/20120116170758/https://pastebin.com/HakCdFW1), timestamp **2012-01-16T17:07:58Z**. The recovered `unknown.asc` file (Git blob SHA-1 `0e69b063b379a8ccdd8a96815de318bcf65a1247`) contains the one-time warning, 112-digit modulus, encrypted payload and signature packet naming key ID `7A35090F`. The matching extracted payload `unknown.pem` has Git blob SHA-1 `087ed31790eb8931d0255efd34e137ad13163b35`.

This is a **provenance-qualified mirror of the participant's message**, not a byte-preserving capture of the original onion HTTP response. The archive README says only the `quaetrix0` example has a valid PGP signature; the `unknown` and `another_unknown` copies are redacted and their signatures do not verify. Do not describe this copy as cryptographically authenticated. Separately, the valid 2012 `quaetrix0` sample and the 2016 signed message both verify under the same Cicada primary key; both source texts explicitly use short key ID `7A35090F` for signature authentication, not as an address. The 2016 issuer-ID/address-role gate is documented in [the OpenPGP address-role report](../im-results/lp2-openpgp-issuer-id-address-gate.md). The original emailed `/NUM` token is not present in the message or the Pastebin capture.

**Reproducible interpretation.** The `unknown.pem` payload decompresses to a serialized 188-byte `Cyphertext` field: four 47-byte RSA blocks. Using the archived `unknown.private` and `unknown.factors` values (`p*q=n`), the exact `Crypt::RSA` 1.99 implementation recovers four 5-byte blocks and concatenates them to **`29201928111913239376`**. This is the number to enter at the same participant-specific URL according to the message text; it is **not** the emailed `/NUM` path token.

The compatibility detail matters: `Crypt::RSA::ES::OAEP` uses an encoded-message length of `k-1`, while its `DataFormat::mgf1` increments the 4-byte counter by SHA-1's digest length (**20**) rather than by one. Reproducing the source implementation's counters (0, 20 for a 26-byte mask) succeeds; standards-compliant MGF1 does not. The exact source is pinned at [gitpan/Crypt-RSA commit 257f59d](https://github.com/gitpan/Crypt-RSA/tree/257f59d25d2d4adec3ef7e439e89b07a3a21a4ec), especially [OAEP.pm](https://github.com/gitpan/Crypt-RSA/blob/257f59d25d2d4adec3ef7e439e89b07a3a21a4ec/lib/Crypt/RSA/ES/OAEP.pm) and [DataFormat.pm](https://github.com/gitpan/Crypt-RSA/blob/257f59d25d2d4adec3ef7e439e89b07a3a21a4ec/lib/Crypt/RSA/DataFormat.pm).

**Independent cross-check.** The separate `another_unknown.pem` message decrypts under its own modulus/factors to **`25121996842107342310`**. This matches the subsequent onion path `/25121996842107342310` and the account of the later MIDI email in the 11 June 2021 [participant-style retelling](https://saumitrasapre.medium.com/the-mysterious-puzzle-2-c73d805e1f04). Treat that article as secondary corroboration, not a contemporaneous or signature-verified capture. Its archive payload Git blob SHA-1 is `49e290f2e80502c525f931b35c01232b7ee9bcf4`.

**Finite missing-artifact conclusion.** The recovered copy and RSA response are real progress, but the original `/NUM` token and original onion response bytes remain absent. The exact missing record is the initial email from the puzzle sender containing the unique path number, or a server/request log that maps that number to the one-time response. No public source found in this task provides it. Do not brute-force or guess the path token. This historical page recovery and the MIDI stage do not establish an LP2 cipher, key, plaintext, or p56 preimage. See [full reproduction report](../im-results/2012-rsa-participant-page-recovery.md) and [standard-library reproducer](../sims/2012_rsa_oaep_reproducer.py).


### 2012 MIDI chorus and wordlist: documented original decode, not a 7×7 traversal

**Participant-specific sample limitation.** The pinned 49-word `words.txt` establishes the length and content of **this archived example**. A [separate preserved 2012 participant account](https://github.com/cicada-solvers/The-Complete-Cicada3301-Archive/blob/main/2012/MIDI%20puzzle/Cicada%203301%20Puzzles.txt) explicitly calls the assignment a *unique list of words* and preserves a different redacted example, `***** garden ball house cat shore back head galon` (eight words visible, redacted extent unknown). The separately preserved account is not a cryptographically verified original server transcript. It suffices to prevent claiming that the 49-word count was fixed for all recipients. The comparisons below remain valid for the specific 49-word artifact and do not establish a universal 7×7 cross-round constraint.

**Established historical solve, independently reproduced 11 November 2026.** The original [2012 MIDI-stage archive README](https://github.com/neuroretransmit/cicada/blob/main/2012/009-midi-puzzle/README.md) and its [`decode.py`](https://github.com/neuroretransmit/cicada/blob/main/2012/009-midi-puzzle/decode.py) already explain the exact operation. The decoded first musical track instructs participants to create a GPG key, encrypt and sign **their supplied wordlist** with Cicada's key, then submit it to the address that sent the participant's numbers. The archived example here contains 49 words; the source does not establish that 49 was a fixed stage-wide word count. The second track decodes to the signed Blake stanza repeated **three times**, which supplies the announced chorus/crib. The 49 words are an actual encrypted-submission payload; their 7×7 count does not by itself prescribe grid positioning, start cell, eight-direction map, or next-page address.

A fresh binary parser against archived [`song.mid`](https://github.com/neuroretransmit/cicada/blob/main/2012/009-midi-puzzle/song.mid) (Git blob `11924e0e195208c2eea757655035e149fb8a190f`, 10,889 bytes) reproduced **558** track-1 note-off events and **714** track-2 note-off events. With MIDI event **note-off delta** times, the distinct `note + note_off_delta` sums number **25** and **23** respectively. In this monophonic file, every note-off delta equals its paired note duration; it is not an absolute start timestamp. The MIDI explicitly records **7/2** meter at 96 ticks/quarter (1,344 ticks/bar). Track 2's 714 events are three identical 238-event cycles, each lasting 30,912 ticks or **23 bars**; the same track has 23 distinct pitch-duration pairs. This is an exact internal 2012 structure, not a GP29 key. Sorting these sums and mapping to the historically published alphabets `abcdefghiklmnopqrstuvwxyz` and `abcdefghijklmnoprstuvwy` recovers the same full messages printed in the archive README, including this archived first track's 49 words and the second track's three complete stanza repetitions. Source details: format 1, 96 ticks/quarter, three tracks (metadata plus two note tracks); note pitches are exactly 55/56/58/60/61/63/65/67 and their octave-lower counterparts 43/44/46/48/49/51/53/55.

A separate raw-timing gate tested the source-visible alternatives. Track 1 has 30 unique `pitch + note_on_delta` values and Track 2 has 26; assigning the most frequent Track-1 value (61, 95 occurrences) to space and mapping the remaining 29 sorted values to GP29 order yields no readable text. Pitch plus within-bar position gives 315/345 states and pitch plus bar index gives 72/82. No source-selected timing interpretation yields a 29-symbol alphabet or reusable LP2 key. The 23 bar note-on counts also fail a direct p36 line-length match and cannot partition its 50 hyphen-delimited groups into 23 consecutive blocks; see the timing report's p36 alignment check. See [the raw timing gate](../im-results/2012-midi-chorus-p36-238-gate.md#4-raw-midi-timing-and-gp29-key-source-gate-agent34) and [its parser](../sims/2012_midi_timing_source_gate.cjs).

### 2012 chorus ↔ p36 238-symbol alignment: exact length, direct routes rejected

The first decoded Track-2 Blake chorus has **238 alphabetic characters**, exactly matching the **238 GP29 runes** on physical p36; p36 is the only LP2 page with that rune count. The archived MIDI has 714 Track-2 note-off events, a 238-event sequence repeated three times. The first cycle's 23 distinct note-plus-delta sums, ranked by the source's alphabet abcdefghijklmnoprstuvwy, reproduce the 238-letter stanza. This is a concrete source-derived alignment, but page36 selection is retrospective and the archived MIDI copy/PGP signature was not independently authenticated in this run.

Bounded tests reject direct use: additive/subtractive GP-index, Latin-ordinal, source-rank, MIDI-sum-mod29, GP-prime and phi(prime) pads all remain near uniform IoC; the stanza is not p36 under direct monoalphabetic or homophonic substitution, no affine monoalphabetic map exists, and a source-ordered adjacent-pair affine Hill map over GF(29) fits only 3/119 pairs. The stanza has 56 words versus p36's 49 page-local words. The archived 2012 49-word submission list is participant-specific and is not a universal key. The independently derived 2014 p50 degree-238 residual Q238 was also compared in both coefficient orders with the chorus, source ranks, note+delta residues and p36 crib keystream: no exact relation; the best post-hoc affine relabeling reaches only 20/238, not a source-selected operation.

**Decision:** retain the 238/238 alignment as an unresolved clue, but retire the tested direct crib and running-key interpretations. Do not expand into arbitrary phase/reversal/transposition sweeps without an original source selecting the operation.
