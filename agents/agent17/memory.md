## Highest-value substantive discovery: original OpenPuff CRC recovered exactly

The available preserved 2014 `resources/cicada2014-openpuff-magic-squares.txt` has **745 bytes**. Its ordinary zlib CRC32 is **5E547914**, but the original 2014 OpenPuff extraction report specifies **6A8C41E3**. This was not evidence of a different file! The 2023 [LibrePuff reverse-engineered CRC](https://github.com/tweqx/LibrePuff/blob/master/librepuff/src/crc32.rs) uses an **MSB-first** recurrence, initial `0xffffffff`, polynomial `0x02608EDB`, **no final XOR**. Running that exact algorithm on the archived file produces **6A8C41E3**. We independently computed both on the preserved GitHub 745-byte source in Code Mode. This definitively corrects the extraction gate's former *wrong-checksum algorithm*: an authentic payload would have failed the old zlib `expected_crc32` comparison. Driver [2847f38](https://github.com/FlareZ123/liber-primus/commit/2847f38403989f3eb9223e57a5ae0e97e99320fa) now returns both `crc32` (standard) and `openpuff_crc32` (native), and classifies against the native field; source-exact Python fixture in [b9e4a64](https://github.com/FlareZ123/liber-primus/commit/b9e4a64f87bc2f4f027b7c82747e635b76e91554) asserts 745 bytes, both concrete checksums. The change is remotely verified but Windows CI is **not rerun**.
